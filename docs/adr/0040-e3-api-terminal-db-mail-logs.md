# ADR-0040 — API do E3: terminal no daemon, famílias de manifesto para bancos e e-mail, `logs.targets`, configuração e extras de segurança

**Status:** aceito · **Data:** 2026-10-28 · Segundo contrato do M2, segue a regra de crescimento da [ADR-0039](0039-error-details-and-shell-api.md) §1 (um PR de contrato por épico, tudo aditivo, `API_VERSION` 1.1). Estende a [ADR-0009](0009-remote-ready-ipc.md), a [ADR-0015](0015-ipc-protocol.md) (streams com `seq` e `resume_from`) e a [ADR-0046](0046-logs-seq-domain.md) (domínio de `seq` dos logs).

## Contexto
As telas complementares do M2 ([07 §5.6–5.11](../07-ui-ux.md)) — Bancos, Mail, Logs, Terminal, Configurações e Diagnóstico — e os extras de segurança (desinstalar a CA, encerrar quem ocupa uma porta, ver o `.env` de um site) precisam de métodos, campos e eventos que a API 1.0 não tem. O E3 roda em vários worktrees em paralelo (backends T4–T11, telas T12–T20); se cada tarefa mexesse em `methods.rs`, `events.rs`, `generated.ts` e `not_implemented.rs`, os merges colidiriam a cada PR. Por isso este PR fixa **todo** o contrato do épico de uma vez, com os métodos respondendo `not_implemented` com a tarefa dona até o backend chegar.

Quatro escolhas de forma precisavam de decisão: onde vive o terminal integrado; como o daemon sabe o que é banco de dados ou caixa de e-mail sem código por tool; como a GUI descobre e pagina os logs; e como a tela de Configurações é gerada sem conhecer cada chave.

## Decisão
1. **Contrato primeiro, aditivo, `API_VERSION` 1.1.** Nada é removido nem renomeado; campos novos têm `#[serde(default)]` (um cliente 1.1 lê um daemon 1.0 e vice-versa), saídas opcionais de alto volume não são serializadas quando vazias (`LogLineDto.access`). Todo método novo entra em `METHODS` com papel e flags explícitos, em `NOT_IMPLEMENTED` com a tarefa (`M2-E3-T4`…`T11`; `db.open` passa para **M3-E1**) e, quando tem comando, com `cli_template`, stub no clap, linha no golden de templates e linha na tabela de `forge-cli/tests/commands.rs`. Um parâmetro novo de um método que já funciona e cujo backend é de outra tarefa responde `not_implemented` em vez de ser ignorado (`logs.read {before_seq}` → M2-E3-T8): ignorá-lo devolveria as linhas mais novas de novo a quem pagina para trás.
2. **Sessões de terminal no daemon (`terminal.*`, `TerminalId` ULID).** `terminal.open {dir?, site?, versions, shell?, command, env, cols, rows, title?} → TerminalDto`, `terminal.list`, `terminal.input {id, data, input_seq}`, `terminal.resize`, `terminal.close`, stream `terminal.subscribe {id, resume_from}` (notificações `terminal.output`/`terminal.lagged`, item `TerminalItemDto = output{data} | exited{exit_code}`), `terminal.unsubscribe` e evento `terminal.exited {terminal_id, exit_code, site_id}`.
   - O pseudo-console é um ConPTY próprio atrás de um trait `PtySpawner` do `forge-core` (Win32 só em `platform/windows`, M2-E3-T3); o processo entra no Job Object **antes** de retomar a thread (`CREATE_SUSPENDED`), por isso não se usa `portable-pty`. As sessões sobrevivem a recarregar a GUI e a quedas de conexão (o cliente reanexa com `terminal.list` + `resume_from`) e morrem com o daemon (JobTree).
   - Todos os métodos são **`admin`** e **nenhum é `local_only`**: o processo roda na máquina do daemon, então um admin remoto ganha um shell remoto, como SSH ([13 §2](../13-remote-mode.md)); o papel é a barreira. Sem comando da CLI (o equivalente mostrado pela GUI é `forge shell`); `terminal.unsubscribe` é built-in do servidor IPC, como `logs|metrics.unsubscribe`.
   - O `seq` do stream é um **offset em bytes**: um item `output` leva o total de bytes produzidos até o fim do seu `data` (o offset logo depois dele), então `resume_from: N` reenvia a partir do byte `N`; o item final `exited` leva bytes + 1. A saída fica num anel de 1 MiB por sessão; cursor mais antigo que o anel recebe `terminal.lagged {missed}` (bytes) e depois o anel inteiro — o cliente limpa a tela e reproduz. Assinante lento perde os mais antigos (drop-oldest), nada espera por ele.
   - `terminal.input` **não** é `mutating`: o cache de idempotência por `request_id` guardaria cada tecla; duplicatas são descartadas por sessão pelo `input_seq` estritamente crescente do cliente. `terminal.open` e `terminal.close` são `mutating` (retentar não abre duas sessões); `terminal.resize` é idempotente por natureza.
3. **Bancos e e-mail por famílias declaradas no manifesto, nunca por tool.** Blocos opcionais `spec.database` (família de protocolo, cliente e seu runner, templates SQL, dump/restore/shell, `url`/`env`) e `spec.mail` (família de API `mailpit-v1`, nomes de porta, `env`) entram no schema (M2-E3-T2); o daemon roda os clientes declarados com validação estrita de identificadores antes de qualquer substituição.
   - `DatabaseListDto.instances: [DbInstanceDto {instance_id, instance, tool, version, protocol, state, port, data_size_bytes?, capabilities{create, drop, export, import, shell, url, open_with}}]` lista **todas** as instâncias de banco (também paradas), para a GUI nunca adivinhar pelo id da tool. `protocol` é string (`mysql`, `postgresql`): o conjunto vem de dados do registry, e um daemon mais novo pode trazer uma família que um cliente antigo não conhece.
   - `db.shell` passa de `Ack` para **`ShellCommandDto {program, args, cwd?, env}`** — uma quebra segura, porque nunca foi implementado e o único cliente (`forge`) muda neste PR. A CLI roda o comando preso ao console e sai com o código dele (`--json` imprime o comando); a GUI o abre num terminal integrado (`terminal.open {command}`). `env` pode trazer credenciais (`MYSQL_PWD`, `PGPASSWORD`) e nunca é logado.
   - `db.export` grava `.sql.zst` pela crate `zstd` (M2-E3-T6). `db.open`, a seção Redis, usuários de banco e backups agendados ficam para o M3 (nota em [07 §5.6](../07-ui-ux.md)).
4. **E-mail.** `MailListParams.query|offset`, `MailListDto.total` (mensagens que casam com o pedido: há mais páginas enquanto `offset + messages.len() < total`) e `unread` (da caixa inteira, o selo), `MailMessageDto.cc|bcc|reply_to|attachments[MailAttachmentDto]`, `MailShowParams.mark_read` (padrão `true`, o comportamento de antes; só vale para `operator` ou acima — um `viewer` lê sem alterar a caixa). Métodos `mail.mark_read {ids, read}` e `mail.delete {ids, confirm}` (`operator`, `mutating`) e `mail.attachment {id, part_id}` (`viewer`) → `MailAttachmentContentDto` em base64, **no máximo 4 MiB** decodificados (`MAIL_ATTACHMENT_MAX_BYTES`: base64 cresce 4/3 e o quadro do IPC tem 8 MiB); maior → `invalid_input` apontando a UI do Mailpit. O evento `mail.changed {instance_id, messages, unread, new_messages}` sai de um vigia do daemon que consulta `/api/v1/info` a cada 3 s só com a instância rodando e publica só quando as contagens mudam: as telas e o selo nunca fazem polling. O HTML da mensagem é conteúdo não confiável: a GUI o mostra num `iframe srcdoc` sem scripts, sem same-origin e com imagens remotas bloqueadas (M2-E3-T13, [11](../11-security.md)).
5. **Logs.** `logs.targets → LogTargetListDto {targets: [{target, label, kind, group, format?, live, file?}]}` lista o que `logs.read|subscribe` aceitam; `kind` (`daemon`, `instance`, `instance_file`, `pool`, `site`, `app`) é enum porque espelha a gramática fechada dos alvos de [09](../09-cli.md) (um alvo novo exige sintaxe nova, que um cliente antigo também não usaria). `LogsReadParams.before_seq` pagina para trás sobre o `seq` monotônico da [ADR-0046](0046-logs-seq-domain.md). `LogLineDto.access {host, status, method, uri, rt_ms?, upstream?}` preenche as linhas de `site:<host>`, pelo único parser de access log (o do `forge-metrics`, M2-E5-T3) escolhido pelo formato do manifesto, nunca pelo id da tool. Quem lista arquivos ignora o sidecar `.seq` e os `.1`…`.N`. O cliente junta até 8 assinaturas; o `LogViewer` é um só (M2-E3-T12) e substitui a aba mínima de Logs do E2.
6. **Configuração.** `system.config_list → ConfigDocumentDto {values, defaults, schema, set_keys}`: valores efetivos e padrões na forma aninhada do `forgebox.toml`, o JSON Schema (schemars) que os valida e as chaves pontuadas definidas no arquivo — a tela de Configurações é gerada do schema. `ConfigValueDto.requires` lista ações de seguimento que a mudança pede e o daemon não faz sozinho, como nomes de método (`tls.ca_rotate` depois de trocar o TLD, `daemon.restart`). Evento `config.changed {keys, requires}` a cada escrita, de qualquer cliente. As escritas passam por um único dono, o que corrige atualizações perdidas de leitura-modificação-escrita; o que dá para aplicar ao vivo é aplicado (DNS liga/desliga, re-render ao trocar o TLD) (M2-E3-T10).
7. **Diagnóstico.** `CheckDto.fix_method|fix_params` nomeiam um método que corrige a checagem (`dns.policy` → `net.dns_enable`, `tls.ca_trusted` → `tls.ca_install`, `path.user` → `shell.path_add`); o cliente só roda o que está na **sua** allowlist e depois repete a checagem. O texto `fix` continua para a CLI.
8. **Extras de segurança** (análise de ameaças na ADR-0045, M2-E3-T11):
   - `tls.ca_uninstall {scope}` (job, `admin`, `mutating`; `local_machine` pelo `forgebox-helper`, com a mesma validação da instalação), idempotente, publica `tls.ca_untrusted {scope, thumbprint_sha1}`.
   - `services.kill_port_holder {port, pid, confirm}` (`admin`, `local_only`, `mutating`): o daemon confere de novo que o `pid` ainda segura a porta e que não é processo do Forgebox, o próprio daemon, processo crítico/de sistema nem serviço, encerra e publica o evento de auditoria `port.holder_killed {port, pid, exe, client}`. A CLI (`forge service kill-port <porta> [--pid]`) mostra o dono e pergunta.
   - `sites.env {site, reveal?} → SiteEnvDto {site_id, host, files[{name, path, vars[{key, value?, secret, line}]}], revealed}`: o daemon lê `.env`/`.env.local` do site; valores de chaves secretas (`PASS`, `SECRET`, `KEY`, `TOKEN`, DSN com credencial) vêm como `null` — mascarados nunca saem do daemon. O método é `operator`; `reveal: true` exige `admin`, conferido pelo handler (a tabela tem um papel por método).
9. **Eventos.** `mail.changed`, `terminal.exited`, `config.changed`, `tls.ca_untrusted` e `port.holder_killed` entram em `EventKind`, `EVENT_PAYLOADS` (payloads com `v`), [03 §8](../03-engine.md) e nos reducers/invalidações da GUI (um reducer ou um `ignore` com motivo por kind).

## Alternativas descartadas
- **Terminal no processo da GUI (PTY aberto pelo `src-tauri`):** violaria "GUI só depende de `forge-ipc`" e "Win32 só em `platform/windows`", morreria com a janela, não serviria a um daemon remoto e duplicaria o ambiente do Forgebox (PATH, versões do site) que o daemon já monta para `shell.env`.
- **`portable-pty`:** não deixa criar o processo suspenso para entrar no Job Object antes de rodar; um filho que nasce fora do Job pode sobreviver ao daemon. O preço é manter o ConPTY próprio, atrás de um trait testável com falso.
- **Terminal `local_only`:** a GUI remota perderia o terminal, sem ganho de segurança — o processo roda no daemon de qualquer jeito; quem barra é o papel `admin`.
- **`terminal.input` `mutating`:** cada tecla ocuparia uma entrada do cache de idempotência; o `input_seq` resolve retentativas sem custo no servidor.
- **`seq` do terminal por chunk (contador):** a retomada exata depois de uma queda precisaria mapear chunks para bytes do anel; o offset em bytes é a própria posição no anel e dá a contagem exata de perdidos.
- **Métodos por tool para bancos/e-mail (`mysql.*`, `mailpit.*`):** é lógica por tool em Rust; famílias declaradas no manifesto cobrem MySQL/MariaDB/PostgreSQL e Mailpit com um motor só.
- **`db.shell` mantendo `Ack` e abrindo uma janela pelo daemon:** a CLI não ficaria presa ao console de quem chamou e a GUI não poderia embutir o cliente; um comando devolvido serve aos dois.
- **`protocol`/`shell` como enums:** um valor novo vindo de dados quebraria a desserialização da lista inteira num cliente antigo. `LogTargetKind` é enum porque espelha uma gramática fechada.
- **GUI consultando o Mailpit (ou `mail.status`) periodicamente:** N clientes × polling; um vigia no daemon é a fonte única, e `mail.changed` cobre CLI, GUI e bandeja.
- **`sites.env_reveal` separado (`admin`):** dobraria os métodos e os templates; um parâmetro conferido no handler mantém uma linha só, com o teste de papel na tarefa do backend.
- **Ignorar `before_seq` até o backend existir:** paginação silenciosamente errada; `not_implemented` com a tarefa é honesto e a GUI desabilita o controle.

## Consequências
- Os backends do E3 (T4–T11) e as telas (T12–T20) trabalham contra tipos gerados já mesclados; cada backend remove suas linhas de `NOT_IMPLEMENTED` (e do espelho `apps/desktop/src/ipc/fixtures/not-implemented.json`, conferido por um teste do `forge-daemon`) e troca as linhas `NI` da tabela da CLI pelo resultado real.
- Comandos novos do `forge`: `logs --list`, `logs <alvo> --before <seq>`, `mail list --search|--offset`, `mail show --keep-unread`, `mail show <id> --attachment <parte> [-o arquivo]`, `mail read <id>... [--unread]`, `mail delete <id>...`, `config list`, `tls ca uninstall [--scope]`, `service kill-port <porta> [--pid]`, `site env <site> [--reveal]`; `db shell` roda o comando devolvido. Sem CLI: `terminal.*` e `shell.open_editor` (só GUI).
- `local_only` passa a incluir `shell.open_editor` e `services.kill_port_holder`; `terminal.open` é a exceção documentada à regra "quem abre algo é local" (abre no daemon).
- Quebra única e segura: `db.shell` → `ShellCommandDto`. Os nomes da API seguem abertos a ajuste até a tag v0.2.0 (ADR-0039 §1).
- Os eventos `tls.ca_untrusted` e `port.holder_killed` são definidos aqui, antes dos seus produtores (M2-E3-T11), para que o E3 não volte a mexer em `EventKind`/`generated.ts`.
