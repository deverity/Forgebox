# ADR-0029 — Composição do `forgeboxd`: boot limitado, serviços derivados do manifesto, pools por versão, render serializado, `not_implemented` com tarefa

**Status:** aceito · **Data:** 2026-10-27

## Contexto
Até M1-E5-T2 cada crate de domínio existia isolado, testado com fakes: supervisor e atores de instância, pools FastCGI, render com blocos gerenciados, sites, DNS, TLS, registry, providers/layout/updates e a API (`forge-ipc`). O daemon precisava compô-los seguindo o boot de [01 §5.1](../01-architecture.md) sem quebrar as regras que valem para todo o resto: nada de código por tool, Win32 só em `platform/windows`, nada trava o controlador ([ADR-0011](0011-actor-concurrency-model.md)), API remote-ready ([ADR-0009](0009-remote-ready-ipc.md)). O aceite é subir e descer limpo 100 vezes seguidas.

Pontos sem resposta nos docs:
1. Como uma `Instance` vira um `InstanceSpec` (exe, args, stop, health, pré-checagens) sem saber qual tool é.
2. Quem decide qual pool PHP serve cada site e como o servidor web fica sabendo das portas dos workers.
3. Como impedir dois daemons na mesma raiz e o que deixar em disco para clientes e humanos.
4. O que responder nos ~40 métodos do contrato cujo backend é de tarefas futuras (db, mail, share, métricas, remoto...).
5. Para onde vão os eventos publicados (o `resume_from` do IPC lê a tabela `events`) e os logs do próprio daemon.

## Decisão
**Instância única.** Antes de qualquer outra coisa o `main` cria o mutex nomeado `Global\Forgebox.Daemon` (raiz padrão) ou `Global\Forgebox.Daemon-<chave>` (`forge_core::platform::host`, `CreateMutexW` em `platform/windows/host.rs`); a chave é a mesma do pipe (`forge_core::paths::root_instance_key`, FNV-1a da raiz em minúsculas, agora compartilhada por `forge-ipc`). Já existe → mensagem pt-BR e código de saída 4 (conflito) em ~50 ms, sem tocar no store nem nos logs. Depois do IPC aberto o daemon grava `state/locks/forgeboxd.lock` (JSON: pid, versão, mutex, pipe) só como descrição; quem decide é o mutex, que o SO fecha se o processo morrer, então um crash nunca deixa "trava" para trás. O arquivo é removido no fim do shutdown.

**Boot limitado** (`forge_daemon::boot`), na ordem de 01 §5.1. Cada passo que depende do mundo externo tem orçamento e, se falhar sem tornar o daemon inútil, vira log e o boot segue: catálogo do registry carregado do cache em até 10 s (o carregamento continua em segundo plano; refresh periódico é job do scheduler), `discover` de `bin/` em até 20 s, resolvedor DNS só com `[dns] enabled` (nova chave, padrão `true`) e porta ocupada vira aviso, verificação de NRPT/`hosts` só leitura em 5 s. Primeiro registry: o oficial, adicionado na primeira execução (URL raw do repositório, chave `registry/keys/dev.pub` até a release embutir a de produção); `--registry`/`FORGEBOX_OFFICIAL_REGISTRY` trocam a fonte (dev e testes usam a pasta `registry/` do repositório, assinada). Instâncias com `autostart` (ou `desired_state = running`) sobem em ondas por `depends_on`; os servidores web ficam para depois dos pools, para o primeiro render já ter os upstreams.

**Serviços derivados do manifesto** (`forge_daemon::services`). Um `InstanceActor` por linha de `instances` (novo `forge_core::store::InstanceRepo`; a tabela já existia em 0001). Portas de `service.daemon.ports[]` reservadas no alocador (dono `instance/<id>/<nome>`: a porta `default` se livre, senão a primeira livre da faixa); `instance.config.<id>` = `config.files[].path`; `instance.data_dir` = `service.daemon.data.dir`; todas as strings substituídas por `RuntimeVars` (as variáveis de [04 §1.4](../04-tool-manifest-spec.md)). Comandos do manifesto (`stop.command`, `check`, `health.command`, `data.init`, `reload.command`) são divididos por espaço com aspas e o programa relativo é resolvido na pasta da versão. Antes de cada start: render do alvo da tool em `forge-render` (quando existe) e `data.init` uma vez se a pasta de dados não existe. Ferramentas `service.kind: daemon` instaladas ganham uma instância `default` (com o `autostart` do manifesto) no boot e após instalar/descobrir.

**Pools por versão** (`forge_daemon::pools`, `web`). O "PHP" dos sites é a tool cujo manifesto declara `service.kind: pool` (nenhum id fixo). Cada site `php` habilitado resolve para uma versão instalada: versão exata fixada, ou a **versão ativa** da série no motor de updates (`forge_provider::update::policy::active_versions`: depois de um rollback serve a versão retida, não a mais nova instalada), ou, sem série, a série ativa mais nova. A tabela de pools é por `VersionId` (os donos de porta dos workers são `pool/<version id>#worker-<n>`, então duas tabelas por nome de upstream colidiriam). O nome do upstream do pool é o da série (`php_8_3`); um site com versão exata (`php_8_3_36`) recebe um upstream-alias com os mesmos servidores no render. `PoolSpec` sai de `service.pool` (args com `{{ port }}` preservado, `config.env` + `pool.env`, scaling, recycle, `runtime_deps`, `expect_php_version` = versão instalada). Pools sem site são parados no reconcile. O motor de updates troca pools pelo `Switcher` do `forge-fcgi` (`DaemonPoolSwitcher`).

**Render serializado.** `WebManager` é ao mesmo tempo o `UpstreamListener` de todos os pools e o renderizador das instâncias: monta o `RenderContext` (sites do servidor, upstreams dos pools em execução, portas `http`/`https` da instância) e aplica o alvo com blocos gerenciados — edição do usuário dentro de um bloco é mantida e publicada como `config.drift_detected`, nunca sobrescrita. Uma única vez (semáforo de uma permissão com timeout) serializa os renders; quem segura a vez nunca inicia pool, então um pool que chama o listener durante o próprio start não trava. Servidor em execução com arquivo alterado: `reload.command` do manifesto (ou restart). Sites seguros pedem a folha ao ator `tls`; sem certificado, o site sai em HTTP com aviso no log. O scheduler reage a `site.*`, `tool.updated|rollback|install.completed` e `tls.renewed` com reconcile (debounce de 300 ms).

**Endpoint interno** (`forge_daemon::internal`): HTTP/1.x mínimo em `127.0.0.1` na porta da nova faixa `internal` (47481, reservada para o dono `daemon/forgeboxd/internal`), sobe antes do primeiro render e vai para `prefs.internal_port` dos templates; atende `/_forgebox/starting?host=` (página dos processes `on-visit`, `AppManager::starting_page`) e `/_forgebox/health`. Uma requisição por conexão, cabeçalho de até 8 KiB lido em 5 s.

**Nomes longos.** O `forgeboxd` cria a raiz e passa a usá-la com nomes longos (`GetLongPathNameW` em `forge_core::platform::long_path`, sem resolver junctions) antes de tudo; pastas de versão lidas do store, raízes de site no render e pastas de `sites.add` também. A chave do pipe/mutex expande a raiz, para cliente e daemon concordarem mesmo quando um deles chegou por `GUSTAV~1`.

**Eventos e logs.** Uma tarefa assina o barramento antes de qualquer publicação (assinatura e ponto de retomada atômicos via `subscribe_from`), grava em lotes de até 256 pela thread de escrita, recupera do anel em memória o que perdeu se ficar para trás e mantém 50 000 linhas (docs/01 §6). O barramento nasce com o maior `seq` da tabela, então `seq` continua entre execuções (verificado no laço de 100). Logs do daemon: `tracing` em JSON lines por `tracing-appender` com rotação diária em `logs/forgeboxd.log.<AAAA-MM-DD>` (14 arquivos), escrita numa thread própria; `--foreground` acrescenta stdout legível; a feature `console` troca tudo pelo tokio-console (`--cfg tokio_unstable` só nela).

**Contrato inteiro respondido.** Todo método de `METHODS` tem handler: backend real ou `not_implemented` com a mensagem `"<método> is not implemented yet: <o quê> (roadmap <tarefa>)"` (`forge_daemon::api::not_implemented`, tabela única; o teste de integração chama todos os métodos e confere código estável e tarefa). `daemon.stop {keep_services: true}` também responde `not_implemented`: os serviços vivem no Job raiz do daemon e morrem com ele; manter a stack exige o handoff de Jobs do self-update (docs/05 §5).

**Shutdown** (`forge_daemon::shutdown`): scheduler e watcher de pastas param, jobs são cancelados, pools + processes de sites + instâncias param **em paralelo** dentro de um orçamento global (`--shutdown-timeout`, 30 s), o que sobrar no Job raiz é terminado e aguardado, atores param, `daemon.shutdown` é publicado e entregue (100 ms) antes de a API fechar (o pipe some com o último handle), o log de eventos esvazia, o store faz flush e fecha, o arquivo de lock sai e o mutex é liberado. `daemon.restart` repete isso e inicia um daemon novo destacado (`spawn_detached`, fora do Job quando permitido).

## Consequências
- Boot de uma raiz vazia ~130–200 ms até o pipe responder; shutdown ~145 ms (laço de 100: médias 131 ms e 144 ms). Com um pool PHP real o pipe abre depois do pool aquecer (~0,6 s).
- O boot espera o start das instâncias com `autostart` (cada uma limitada por `start_timeout`); um serviço lento atrasa a abertura da API até esse prazo, não para sempre.
- O alvo de render continua sendo tabela do `forge-render` por id de tool (`targets::by_id`); o daemon só pergunta "existe alvo?" e "tem arquivos por site?" (servidor web). Quando o manifesto declarar seus arquivos (docs/03 §3.2.1), nada muda aqui.
- Pastas estacionadas novas (`sites.park`) entram no reconcile na hora, mas o watcher só passa a observá-las no próximo boot.

## Alternativas rejeitadas
- *Arquivo `.pid`/lock como instância única*: sobra após crash e exige heurística de "processo ainda vivo"; o mutex nomeado é liberado pelo SO.
- *Abrir a API antes do boot terminar*: a GUI veria um daemon "pronto" sem catálogo nem serviços; `daemon.ready` perderia o sentido. A API abre no passo 9, como no doc, e cada passo tem prazo.
- *Pools por nome de upstream*: colidiria nos donos de porta (por versão) e complicaria o blue/green, que troca por `VersionId`.
- *Listener de upstream passando pela caixa de mensagens de um ator "web"*: um pool chamando o listener enquanto o mesmo ator espera o start desse pool travaria até o timeout; a vez (semáforo) com a regra "não iniciar pool segurando a vez" resolve sem ator.
- *Responder `method not found` nos métodos futuros*: o cliente não distingue "ainda não" de "versão errada da API"; `not_implemented` com a tarefa é estável e informativo.
- *`keep_services` fingindo funcionar*: o `KILL_ON_JOB_CLOSE` do Job raiz mataria tudo ao sair; melhor recusar explicitamente.
