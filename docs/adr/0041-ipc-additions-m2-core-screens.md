# ADR-0041 — API do E2: catálogo, releases e plano de instalação, histórico, ícones, quick settings, configurações avançadas, driver e certificados

**Status:** aceito · **Data:** 2026-10-29 · Terceiro contrato do M2, segue a regra de crescimento da [ADR-0039](0039-error-details-and-shell-api.md) §1 (um PR de contrato por épico, tudo aditivo, `API_VERSION` continua 1.1). Estende a [ADR-0009](0009-remote-ready-ipc.md), a [ADR-0015](0015-ipc-protocol.md) e a gramática de templates da [ADR-0037](0037-cli-equivalent-templates.md) (sem mudá-la).

## Contexto
As telas núcleo do M2 ([07 §5.1–5.5 e §5.9](../07-ui-ux.md)) — Onboarding, Dashboard, Serviços, Sites, PHP e Catálogo — precisam de dados que a API 1.0 não tem: metadados do catálogo (tipo, resumo, cor, ícone, plataformas, tamanho, rótulos das variantes, conteúdo das stacks), as versões que os providers publicam, o plano do que uma instalação baixaria (com o total), o histórico de updates, os quick settings com valores atuais ([04 §1.3](../04-tool-manifest-spec.md)), as configurações avançadas de uma instância (args, env, política de reinício, versão), o override do driver de um site, a lista de certificados com validade e confiança e a correlação entre processos de site e os eventos `service.*`. Os backends do E2 (T4–T10) e as telas (T12–T19) rodam em paralelo; este PR fixa **todo** o contrato do épico de uma vez, com os métodos respondendo `not_implemented` com a tarefa dona até o backend chegar, como o E3 fez ([ADR-0040](0040-e3-api-terminal-db-mail-logs.md) §1).

Cinco escolhas precisavam de decisão: o que é job e o que é call; como representar releases e planos (por versão ou por build, tamanhos estimados); como a tela de configuração recebe valores tipados se `services.set` só recebe texto; como `services.update` aceita "limpar" listas sem que o comando `forge` equivalente minta; e como o mesmo comando `forge service set` serve leitura e escrita.

## Decisão
1. **Contrato primeiro, aditivo, `API_VERSION` 1.1.** Campos novos com `#[serde(default)]` (o JSON de um daemon 1.0 lê com padrões; `CatalogEntryDto.native` assume `true`, que era verdade para todo o catálogo 1.0). Todo método novo entra em `METHODS` com papel e flags explícitos, em `NOT_IMPLEMENTED` com a tarefa, e — com comando — com `cli_template`, stub no clap, entradas no golden de templates e linhas na tabela de `forge-cli/tests/commands.rs`. As linhas do E2 que citavam só o épico passam a citar a tarefa (`services.set` → M2-E2-T7; `php.ext_enable|disable`, `php.xdebug` → M2-E2-T9). Parâmetro novo de método que já funciona responde `not_implemented` em vez de ser ignorado: `tools.install|remove {target}` → M2-E2-T8 (instalaria/removeria mais do que o pedido), `services.create {data_dir}` → M2-E2-T10 (os dados iriam para outro lugar).

   | Método | Tipo | Papel | Flags | CLI | Tarefa |
   |---|---|---|---|---|---|
   | `tools.releases {tool, channel?}` → `ToolReleasesDto` | job | viewer | — | `forge tool info <t> --versions [--channel]` | M2-E2-T5 |
   | `tools.plan {specs, stack?, variant?, target?}` → `ToolPlanDto` | job | viewer | — | `forge tool install <specs> --dry-run` | M2-E2-T5 |
   | `tools.history {tool, series?, limit?}` → `UpdateHistoryDto` | call | viewer | — | `forge tool info <t> --history` | M2-E2-T4 |
   | `tools.icon {tool}` → `IconDto` | call | viewer | — | — (só GUI) | M2-E2-T4 |
   | `services.settings {target}` → `ServiceSettingsDto` | call | viewer | — | `forge service set <alvo>` sem pares | M2-E2-T7 |
   | `services.update {instance, autostart?, launch?, restart_policy?, version?}` → `InstanceDto` | job | admin | mutating | `forge service update` | M2-E2-T10 |
   | `sites.driver {site, driver?}` → `SiteDto` | job | operator | mutating | `forge site driver <site> <driver\|auto>` | M2-E2-T6 |
   | `tls.list` → `CertificateListDto` | call | viewer | — | `forge tls list` | M2-E2-T6 |

   Nenhum é `local_only`: tudo acontece na máquina do daemon.
2. **Releases e plano são jobs** (rede, prazos por provider, cancelamento por `jobs.cancel`), `viewer` e não `mutating` (não mudam estado; um cache de metadados não conta), como `tools.check_updates`. Nada é baixado.
   - `ToolReleasesDto {tool, releases[], stale, fetched_at?}`: **uma linha por versão** (`version`, `series`, `channel`, `published_at`, `size_bytes` do build preferido, `installed`) com os **builds** dentro (`variants: [ReleaseVariantDto {variant, canonical_name, size_bytes?, installed}]`, preferido primeiro): a tela agrupa por série → patches e escolhe a variante sem perder o tamanho de cada build. Sem acesso aos providers, o daemon devolve o cache com `stale: true` e `fetched_at`.
   - `tools.plan` recebe `specs` **ou** `stack`; com os dois, `specs` substituem a entrada da stack para a mesma tool e acrescentam as outras (o onboarding replaneja depois de o usuário ajustar versões sem perder as extensões da stack). Cada `ToolPlanItemDto` traz `spec` (o que passar ao `tools.install`), versão e build escolhidos, `size_bytes` (do provider; senão a estimativa do manifesto com `size_estimated`), `already_installed`, `reason` (`requested | dependency | stack | extension`, conjunto fechado do resolvedor) e `target` das extensões. `total_bytes` soma o que será baixado, estimativas incluídas (a GUI mostra "≈"); `unknown_size` conta os itens sem tamanho nenhum (fora do total). O resolvedor é o **mesmo** do `tools.install` (M2-E2-T5).
   - O plano de uma **stack não tem comando** (`[!stack]` no template: nenhuma alternativa se aplica e a GUI não mostra comando, nunca um errado); o plano de specs é `forge tool install … --dry-run`.
3. **Metadados do catálogo.** `CatalogEntryDto` ganha `kind` (`tool | extension | stack`), `summary`, `color`, `icon_sha256`, `platforms`, `native`, `official`, `latest`, `update_available`, `size_estimate_bytes`; `description` continua sendo o resumo (nome da 1.0). `ToolInfoDto` ganha `kind`, `description_md` (Markdown não confiável: a GUI renderiza sem HTML cru), `homepage`, `docs`, `changelog_url`, `license`, `variants: [VariantDefDto {key, values, default, labels, derived}]`, `suggests`, `extends` e `stack: StackDto {tools: [{id, series, version, instance, extensions}]}` — `tools.info` passa a valer para extensões e stacks. Já neste PR a busca preenche `kind`, `summary`, `official` e `latest` do índice (dados que o daemon já tem; devolver `tool` para uma extensão seria errado); o resto é M2-E2-T4.
4. **Ícones por hash, nunca embutidos.** `tools.icon` devolve `IconDto {tool, svg, sha256}` do cache verificado do registry, **sanitizado** (≤ 64 KiB; sem `<script>`, `<foreignObject>`, atributos `on*`, referências que não sejam `#id` ou `data:`); a GUI guarda por `sha256` (o mesmo de `CatalogEntryDto.icon_sha256`) e mostra só como `<img>` com data URI, nunca SVG inline ([11](../11-security.md)). Sem ícone: `not_found`.
5. **Histórico.** `UpdateHistoryDto {tool, entries[]}` espelha `update_history` (versões como texto, ids que somem com a versão removida, `trigger: auto | user | rollback`, `status: started | completed | failed | rolled_back`, `rollback_of`), mais novo primeiro; padrão 50, máximo 500.
6. **Quick settings com valor tipado, escrita em texto.** `ServiceSettingsDto {target, tool, settings[], files[], ports[], advanced?}`:
   - `QuickSettingDto {key, label?, kind, options, min?, max?, step?, value?, default?, is_default, apply, file?, also_set, reserve}`; `kind` (`toggle | select | number | text | path | port | slider | multi`) e `apply` (`reload | restart | none`) são enums porque espelham a gramática fechada do schema ([04 §1.3](../04-tool-manifest-spec.md)), como `LogTargetKind` na ADR-0040.
   - `value`/`default` são `SettingValueDto`, união sem tag `boolean | number | string | string[]` decidida pelo `kind` (toggle → booleano; number/slider/port → número; multi → lista; select/text/path → texto); `options` vêm como texto. `services.set` continua recebendo **texto**: `true`/`false`, números decimais, itens de `multi` unidos por `,`.
   - `files` são os `FileRefDto` de `services.config_files` (`role` = `config.files[].id`, o mesmo de `QuickSettingDto.file`); `ports: [{name, port?, default?, protocol, range?}]` mudam com `services.set {"ports.<nome>": …}`.
   - `advanced: InstanceAdvancedDto {autostart, args, env, restart_policy, restart_policy_default, versions}` só para instâncias e **só em conexões `admin`** (o `env` extra pode ter segredos e só um admin o altera); o método é `viewer` porque os valores dos ajustes não são segredo. O papel do `advanced` é conferido pelo handler, como o `reveal` de `sites.env` (ADR-0040 §8).
7. **`forge service set <alvo>` lê e escreve.** Sem pares chama `services.settings`; com `chave=valor` chama `services.set`. O template de `services.set` ganhou a regra `[settings]`: uma chamada com mapa vazio não tem comando (o comando sem pares lê, não escreve). O teste de ida e volta do clap resolve a sobreposição pela mesma regra dos pares.
8. **`services.update` é um patch, e `launch` agrupa args e env.** Campo ausente mantém o valor; a instância é re-renderizada e, se estiver rodando, reiniciada; portas continuam em `services.set ports.<nome>`. `version` só aceita outra versão instalada **da mesma série** (`invalid_input` caso contrário: data dirs não são migrados). `restart_policy: RestartPolicyPatchDto {on?, max?, window_secs?}` muda só o que vem. `launch: LaunchPatchDto {args?, env?}` substitui cada lista presente (`[]`/`{}` limpam) — agrupados porque o comando equivalente não consegue representá-los: argumentos sempre começam com `-` (não representáveis pela ADR-0037) e a regra de verdade da gramática não distingue `[]` de ausente, então uma lista limpa viraria o comando "sem mudança". Com `launch` presente o objeto nunca é vazio e `[!launch]` faz o template não ter comando. CLI: `--autostart|--no-autostart`, `--arg <a>` (repetível, aceita `-…`), `--no-args`, `--env K=V` (repetível), `--no-env`, `--restart never|failure|always`, `--restart-max N`, `--restart-window <segundos>`, `--version <x.y.z>`.
9. **Driver.** `sites.driver {site, driver?}`: com driver, fixa; com `null` (CLI `auto`), detecta de novo pelos arquivos do projeto e grava o resultado; depois re-renderiza. `SiteDto.driver` segue sendo o driver efetivo; não há marca de override (o driver detectado não muda sozinho depois que o site existe) e nenhuma migração.
10. **Certificados.** `tls.list` devolve `CertificateListDto` com todos os leafs de `certs/` (vencidos inclusive, o que vence primeiro antes); `CertificateDto` ganha `ca_thumbprint_sha256` (um leaf de uma CA já rotacionada difere de `CaStatusDto.thumbprint_sha256`) e `trusted: Option<bool>` (emitido pela CA atual e essa CA confiada no store do usuário ou da máquina; `None` quando não conferido, como em `tls.issue`/`tls.renew`). O Dashboard e o Diagnóstico do site usam a validade e a confiança daqui.
11. **Instâncias e processos.** `ServiceCreateParams.data_dir` (absoluto; dentro da raiz ou numa pasta escolhida, nunca em `bin/`), `InstanceDto.data_dir` (já preenchido pelo daemon a partir da linha da instância) e `InstanceDto.size_bytes` (varredura periódica fora do ator, TTL 60 s, `None` até a primeira; M2-E2-T10). `SiteProcessDto.instance_id` e `ServicePayload.site_id` (instâncias de app) deixam a aba Processos seguir o estado pelos eventos `service.*` (`EventFilter.site_id` já casa) sem polling (M2-E2-T6). Nenhum `EventKind` novo.
12. **Detalhe de erro reservado para a troca de PHP.** `sites.php` com uma versão/série não instalada responde `not_found` com `details = {reason: "version_not_installed", args: {tool, requested, installed: [...], fix}}` (M2-E2-T6): a GUI oferece instalar (com o tamanho do `tools.plan`) sem ler a mensagem.

## Alternativas descartadas
- **`args`/`env` soltos em `services.update`** (a lista do plano): o template mostraria `forge service update x` para quem limpou a lista — um comando errado. Estender a gramática da ADR-0037 com uma condição "presente" mudaria os dois renderizadores (Rust e TS) por causa de um método; agrupar em `launch` resolve com a gramática atual. O preço é um nível a mais no JSON.
- **`forge service settings <alvo>` separado:** mais um verbo para decorar; ler com o mesmo comando sem pares é o hábito de `git config`. O preço é a sobreposição documentada no teste de ida e volta e a regra `[settings]` no template de escrita.
- **`kind`/`apply`/`reason` como texto:** perderiam a união exaustiva no TypeScript. O preço da escolha: um tipo novo de quick setting é mudança de schema do manifesto e exige cliente novo para essa tela (o mesmo trade-off de `LogTargetKind`).
- **`value` como JSON livre (`unknown`):** cada tela adivinharia o tipo; a união por `kind` tipa o formulário e o texto do `services.set` fica documentado num lugar só.
- **Releases achatados (uma linha por build):** a tela agrupa por versão; o tamanho de cada build continua dentro da versão.
- **`tools.plan`/`tools.releases` como call:** dependem de rede (até vários segundos) e precisam de cancelamento e progresso.
- **Ícone dentro do `CatalogEntryDto`:** até 64 KiB × centenas de entradas em cada busca; hash + método separado deixa a GUI buscar só o que falta no cache, e de forma preguiçosa.
- **Marca `driver_overridden` no site:** exigiria migração (números reservados para M2-E2-T7 e M2-E5-T7) para pouca informação; "auto" = detectar agora.
- **`services.settings` como `operator`:** os ajustes não são segredo (limites de memória, uploads, portas — que viewers já veem em `services.ports`), e o que pode ser (`advanced`, com o `env` extra) já só vai para admin.

## Consequências
- Os backends do E2 (T4–T10) e as telas (T12–T19) trabalham contra tipos gerados já mesclados; cada backend remove suas linhas de `NOT_IMPLEMENTED` (e do espelho `apps/desktop/src/ipc/fixtures/not-implemented.json`, conferido por um teste do `forge-daemon`), as constantes `EXTENSION_TARGET_TASK`/`SERVICES_DATA_DIR_TASK` e as linhas `NI` da tabela da CLI.
- Comandos novos do `forge`: `tool info --versions [--channel]`, `tool info --history [--series] [--limit]`, `tool install --dry-run`, `tool install|remove --for`, `service create --data-dir`, `service set <alvo>` sem pares, `service update`, `site driver`, `tls list`. Sem CLI: `tools.icon`.
- A GUI ganhou as linhas de `JOB_EFFECTS` dos jobs novos e as consultas novas nos grupos de invalidação (`tools.history` em tools, `services.settings` em config, `tls.list` em tls).
- Os nomes seguem abertos a ajuste até a tag v0.2.0 (ADR-0039 §1).
