# ADR-0025 — Layout de versões: post_install no staging, shims com tabela de aliases e PATH do usuário

**Status:** aceito · **Data:** 2026-10-27

## Contexto
M1-E2-T4 ([10](../10-roadmap-and-agent-tasks.md)) entrega `bin/<tool>/<nome canônico>`, a junction `current` ([ADR-0005](0005-current-junction-switching.md)), shims `.cmd` e o PATH do usuário. Ficavam em aberto:
- em que ponto do pipeline de [03 §5.1](../03-engine.md) o `post_install` roda e o que `{{ paths.version }}` significa enquanto a versão ainda não está em `bin/`;
- como um shim escolhe a versão do projeto (`.php-version`, `.nvmrc`, `forgebox.yaml`) sem falar com o daemon e sem custo perceptível por chamada;
- como saber quais arquivos de versão valem para cada tool e como o Composer (um `.phar`) vira comando, sem `if tool.id == ...`;
- política do PATH: posição, duplicatas, tipo do valor no registro, aviso aos programas abertos, modo portátil;
- como `forge use` convive com uma instalação da mesma tool em andamento.

## Decisão
1. **Pipeline** (`forge_provider::layout::Layout::install_from_archive` → `JobId`): verify → stage (`tmp/stage/<job>/`, com a sensibilidade a maiúsculas de `bin/`) → extract → **`post_install` e `install.verify` na cópia em staging** → move atômico (rename) para `bin/<tool>/<nome canônico>` → `tool_versions` (`ToolVersionRepo::record_install`) → `current` opcional (`CurrentPolicy`, padrão `IfMissing`: só a primeira versão vira `current`) → shims. Falha antes do move não toca `bin/`; falha no registro devolve a pasta ao staging; o staging é sempre apagado. Efeitos do `post_install` fora de `bin/` (`etc/`, `tmp/`) ficam: são idempotentes por contrato ([04](../04-tool-manifest-spec.md) §1).
2. **Duas visões das variáveis**: a *física* (`paths.version` = pasta no staging) vale para a origem de `copy`, destinos dentro da versão e para `run`/`verify` (executável, argumentos, `cwd`, `env`); a *final* (`paths.version` = `bin/<tool>/<nome canônico>`) é o contexto entregue ao renderizador, porque o que vai para `etc/` precisa apontar para o lugar definitivo.
3. `render` passa por um trait `TemplateRenderer` injetado (o daemon liga o `forge-render`; `forge-provider` não depende dele). `run` só executa arquivo **da própria versão** (relativo ou `{{ paths.version }}/...`, nunca via PATH, sem `..`, variáveis ou `%VAR%`), só com `InstallOptions::allow_run` (registry oficial ou manifesto do próprio usuário, [11 §2](../11-security.md)) e via `platform::run_probe_with_env` (Job Object próprio, ambiente explícito, sem janela, timeout padrão 10 min). `install.verify` roda depois do `post_install` e confere a versão impressa (`8.3.36` para `8.3.36+1`).
4. **Turno por tool**: semáforo de uma permissão por tool (mapa sob o `OrderedMutex` `layout.tools`, trava folha), adquirido com timeout (10 s) só na fase final (move, registro, `current`, shims) e em `use`. Download, extração e `post_install` de versões diferentes correm em paralelo; `forge use php` nunca intercala com o fim de uma instalação de php. O PATH tem turno próprio.
5. **`forge use`** (`Layout::use_version`): seleção por nome de pasta > versão exata > série/restrição no esquema da tool (`8.3` = `8.3.*`), empate resolvido por `cmp_builds` (mais nova, depois a preferência de variantes); `LinkFs::replace_junction` (`current.tmp` + rename); duração medida e registrada (≈ 3 ms nesta máquina; aceite < 50 ms); evento novo **`tool.current_changed`** (`ToolCurrentPayload`).
6. **Schema estendido** em vez de lógica por tool: `install.version_files` (arquivos de versão do projeto), `install.project_key` (chave pontuada do `forgebox.yaml`, ex. `spec.site.php`; itens `spec.runtimes[]` com `tool: <id>` valem sempre) e `install.shims` aceitando `{ name, file, interpreter }`. Registry: php declara `.php-version` + `spec.site.php`; nodejs `.nvmrc` e `.node-version`; composer `{ name: composer, file: composer.phar, interpreter: php }`.
7. **Shims `.cmd` gerados** (`layout::shims`): do diretório atual até a raiz do disco, o primeiro diretório com um arquivo de versão (lido pelo próprio `cmd.exe`: primeira palavra da primeira linha que não é comentário `#`) ou com um `forgebox.yaml` que nomeie a versão (lido por `bin/shims/forgebox-project.ps1`, Windows PowerShell iniciado só quando o arquivo existe) decide. A seleção é comparada com uma **tabela de aliases escrita no shim** quando ele é gerado (nome da pasta, versão, versão sem `+build`, `major`, `major.minor`, com ou sem `v`), cada alias apontando para a pasta preferida (`cmp_builds`). Versão pedida e não instalada = erro com a lista do que está instalado (exit 1), nunca *fallback* silencioso. Sem seleção: `current` (ou `bin/<tool>` em `layout: single`). Com `interpreter`, o shim chama `bin/shims/<interpreter>.cmd <arquivo> <args>`, então o `.php-version` do projeto escolhe também o PHP do Composer. Shims são regenerados de forma idempotente a cada instalação (só escreve o que mudou), shims da tool que o manifesto não declara mais são apagados, shim de outra tool ou arquivo não gerado pelo Forgebox nunca é sobrescrito. Todo caminho é relativo ao shim (`%~dp0..\php\<pasta>`): raiz movida ou portátil continua funcionando. Valores lidos de arquivos do projeto só passam por expansão atrasada (`!VAR!`), nunca pelo parser de comandos; nomes de pasta com `% ! " ^ & | < >` ficam fora da tabela. Os `.cmd` são CRLF e ASCII (exceção declarada à regra LF de [15 §7](../15-linux-parity-case-sensitivity.md): rótulos e `goto` do `cmd.exe` falham com LF puro).
8. **PATH do usuário** (`forge_core::platform::UserEnv`; Windows: `HKCU\Environment\Path`): valor lido e escrito cru, preservando `REG_EXPAND_SZ` e os segmentos (inclusive vazios: `a;;b;` volta igual), então adicionar e remover uma entrada restaura o valor byte a byte. Entrada nova vai para o **início** do PATH do usuário; entradas equivalentes (caixa, `/` ou `\`, barra final, `%VAR%` expandido) contam como presentes e duplicatas da mesma entrada são colapsadas; o resto não é tocado. `WM_SETTINGCHANGE("Environment")` só quando o valor mudou, por `SendMessageTimeoutW(HWND_BROADCAST, SMTO_ABORTIFHUNG, 1 s por janela)`. `layout::path::ensure`: `bin/<tool>/current` (+ subpastas de `install.path`) das tools com `current_link`, e `bin/shims` com `[path] shims = true` no `forgebox.toml`; idempotente; com `portable.flag` não escreve no registro. `MemoryUserEnv` serve os testes; o teste contra o HKCU real é `#[ignore]` (manual).

## Alternativas rejeitadas
- **`post_install` depois do move**: `bin/<tool>/<versão>` existiria (visível para `discover` e para a GUI) antes de a versão estar pronta, e desfazer exigiria apagar dentro de `bin/`.
- **`paths.version` = staging também nos templates**: configs em `etc/` apontariam para `tmp/stage/...`, apagado logo depois.
- **Shim que pergunta ao daemon** (`forge which`): latência de IPC a cada `php` e quebra com o daemon parado.
- **Shim em PowerShell ou `.exe` próprio**: PowerShell custa 200–500 ms por chamada; um `.exe` estilo scoop exigiria mais um binário assinado na release. Reavaliar em M2 se o prompt "Terminate batch job (Y/N)?" do Ctrl+C em `.cmd` incomodar.
- **Ordenar versões dentro do `.cmd`**: o `cmd.exe` não compara semver; a tabela gerada em Rust usa exatamente as regras de `forge use`.
- **`if tool.id == "php"` para `.php-version`/Composer**: proibido pelo CLAUDE.md; o schema foi estendido.
- **Acrescentar no fim do PATH**: entradas antigas do usuário (ex. `C:\laragon\bin\php\php` nesta máquina) venceriam o `current` que o usuário pediu ao Forgebox. O PATH do sistema continua antes do PATH do usuário de qualquer forma.
- **`SendMessage`/`SendNotifyMessage`**: o primeiro trava para sempre com uma janela pendurada; o segundo não garante a entrega da string entre processos.
- **`ensure` removendo entradas do Forgebox que não pediu**: o chamador pode passar só parte das tools; remover é explícito (`remove_path_entries`, desinstalador).

## Consequências
- O daemon injeta um `TemplateRenderer` sobre o `forge-render` e decide `allow_run` pela coluna `registries.official`.
- O onboarding chama `ensure_path`; ao instalar uma nova tool de CLI depois disso, o daemon chama de novo (idempotente, nada é transmitido se nada mudou).
- Arquivos de versão em UTF-16 ou com BOM (`echo 8.3 > .php-version` no Windows PowerShell 5.1) não são entendidos: o shim falha com mensagem clara, nunca escolhe outra versão.
- `forge shell` e `tools.which` devem seguir as mesmas regras (`version_files`, `project_key`, `spec.runtimes[]`) reutilizando `layout::select` e o schema.
- Mudanças no registry (`registry/tools/*.yaml`) exigem `cargo xtask registry-index` + `registry-sign` (chave de dev fora do git).
