# ADR-0043 — Extensões (`kind: Extension`) instaladas por versão alvo, vínculo no mapa de variantes

**Status:** aceito · **Data:** 2026-11-03 · Implementa o `target` de `tools.install`/`tools.remove` reservado pela [ADR-0041](0041-ipc-additions-m2-core-screens.md) (M2-E2-T8), sobre o pipeline de instalação da [ADR-0025](0025-layout-staging-shims-user-path.md) e o motor de updates da [ADR-0027](0027-update-engine-active-version-rollback-retention.md).

## Contexto
[04 §2](../04-tool-manifest-spec.md) define `kind: Extension` (`extends`, `compat`, `source`, `install.target` dentro de `{{ paths.version }}`, `post_install`, `toggle`), mas nada o instalava: `tools.install xdebug` dava `not_found` (o catálogo do daemon só via `kind: Tool`) e `--for` respondia `not_implemented`. Uma extensão não tem pasta própria em `bin/`: o arquivo vai para dentro de uma versão instalada de outra tool (`bin/php/8.4.27-nts-vs17-x64/ext/php_xdebug.dll`), e o build certo depende da versão alvo (série, `ts`, compilador). Perguntas:

1. Como escolher o build de cada versão alvo sem lógica por tool (`if tool == "xdebug"`)?
2. Onde registrar "xdebug 3.5.3 está instalado no PHP 8.4.27" sem migration nova (a 0004 é do M2-E2-T7, a 0005 do M2-E5-T7)?
3. O que acontece com a instalação quando a versão alvo é atualizada (`update.migrate` copia `ext/`) ou removida?
4. O que `remove --for` apaga, se o overlay `etc/php/<série>/conf.d/20-xdebug.ini` é da série e não da versão?

## Decisão
1. **Resolução genérica, pelos dados do manifesto** (`forge_manifest::schema::extension`):
   - `compat_for(alvo)`: a primeira entrada de `compat` cujo `tool` (restrição no esquema de versão da tool estendida) casa a versão alvo **e** cujas chaves de `variant` existem no build alvo com o mesmo valor (chave ausente no alvo não casa: DLL de outro runtime não carrega). Sem `compat`, qualquer alvo serve.
   - `release_fits(compat, release, alvo)`: a versão da extensão satisfaz `compat.version`; a variante `<extends>_series` (`php_series`) é igual à série do alvo; as demais chaves da release que o alvo também tem precisam ter o mesmo valor (chaves que o alvo não declara não são conferidas).
   - As releases vêm dos providers de sempre por uma **visão de release** (`ExtensionManifest::release_view`: um `ToolManifest` com os metadados e o `source` da extensão, `semver`, sem variantes declaradas), então URLs com `{php_series}`, hashes curados e checksums de segundo documento funcionam igual às tools.
   - `layout::extension::plan(ext, tool estendida, alvos, explícito, releases, instaladas)`: com `--for php@8.4` (explícito; série = a mais nova instalada da série, ou versão exata), alvo sem build é `not_found` "no build for php 8.0.30 (x64, vs16, nts); compatible php series: 8.5 (vs17, nts), 8.4 (vs17, nts), …"; sem `--for` (ou `--for php`), os incompatíveis são pulados com uma mensagem de progresso e só "nenhum alvo serve" é erro (mesma lista de séries). Alvo não instalado é `version_not_installed` (`not_found`, com `fix`), antes de criar job, exceto quando o mesmo pedido instala a tool estendida antes (`php@8.4 xdebug`).
2. **Uma linha de `tool_versions` por (extensão, alvo), ligada pelo mapa de variantes**: `variant` = variantes da release (`php_series`, `ts`, `compiler`) + `target_tool`, `target_id` (`VersionId` do alvo) e `target_name` (pasta do alvo); `canonical_name` = `<tool alvo>-<pasta alvo>` (`php-8.4.27-nts-vs17-x64`, único por alvo, então reinstalar ou trocar a versão da extensão atualiza a mesma linha via `record_install`); `path` = o arquivo (ou pasta) instalado. O prefixo `target_` é reservado: release de Extension com variante `target_*` é erro de validação (`InvalidId`). Nenhuma migration.
3. **Pipeline** (`Layout::install_extension`, um job por alvo): verify (sha256/tamanho, o mesmo `Verifier`) → extração em `tmp/stage/<job>/payload` (arquivo único recebe o nome de `install.target`) → turno da **tool alvo** → move para `install.target` (arquivo/pasta existente vai para `.<nome>.forgebox-old-<job>` e volta se algo falhar depois) → `post_install` com as variáveis do alvo (`render` vai ao renderizador como `php`, então `{{ series }}`, `{{ paths.version }}` e o modelo `php` são os da versão alvo; `run` nunca executa: extensão não tem executável próprio) → registro → o antigo é apagado. Nada em `bin/` ou `etc/` muda antes da verificação. `tool.install.*` saem com `tool = xdebug` e `canonical_name` da linha. O daemon resolve, planeja, baixa (`DownloadFetcher`) e espera cada job; `tools.install` devolve as linhas por alvo.
4. **Overlay desligado por padrão**: `php/xdebug.ini.j2` sem `php.xdebug` renderiza `;zend_extension = xdebug` (instalado, não carregado); com o modelo (M2-E2-T9) renderiza a seção ligada. O alvo `php` de `forge-render` continua só renderizando `20-xdebug.ini` quando `php.xdebug` existe, então nunca reescreve o arquivo desligado.
5. **Remoção por alvo** (`Layout::remove_extension`): no turno da tool alvo, a linha vai a `removing`, o arquivo é renomeado para `.<nome>.forgebox-removed-<ulid>` e apagado (renomear falhando = `conflict` "carregado por um processo? pare os pools da versão ou desligue a extensão", estado restaurado), os arquivos dos `render` desse alvo são apagados **só se nenhuma outra instalação da mesma extensão renderiza o mesmo caminho** (8.4.26 e 8.4.27 compartilham `etc/php/8.4/conf.d/20-xdebug.ini`), e a linha é apagada. `--for` com tool comum é `invalid_input`.
6. **Ciclo de vida do alvo**: `Layout::remove_version` apaga, na mesma operação do writer, as linhas de extensão ligadas ao `target_id` removido (o arquivo foi junto com a pasta; `RemovedVersion.extensions`); o overlay da série fica, como `php.ini` e `10-forgebox.ini`. No `UpdateEngine::apply`, depois da troca de pools e antes da retenção, `Layout::carry_extensions(de, para)` cria a linha do alvo novo para cada instalação cujo arquivo o `update.migrate` copiou (mesmo caminho relativo à pasta da versão); a linha antiga some com a versão na retenção. Falha vira `warning` do update.
7. **Superfície da API**: `tools.info xdebug` → `kind: extension`, `extends: php`, `homepage/docs/license/description_md` do manifesto, `tool.installed` = uma linha por alvo (ordenadas pela ordem das versões alvo, mais nova primeiro), `policy: manual` (o motor de updates não segue extensões). `tools.install|remove` aceitam extensões; `--variant` com extensão é `invalid_input` (o build segue o alvo). `tools.list` continua listando só `kind: Tool`.

## Alternativas rejeitadas
- **Tabela `tool_extensions` (migration)**: vínculo com chave estrangeira e `ON DELETE CASCADE` seria mais forte, mas colide com a numeração das migrations do M2 e duplica `tools`/`tool_versions` (estado, origem, sha256, tamanho, `installed_at`). O preço do mapa de variantes: a integridade é mantida por código (`remove_version`, `carry_extensions`), e consumidores genéricos de `tool_versions` veem as linhas da extensão (sem manifesto `Tool`, o motor de updates, o agendador e `ensure_defaults` já as ignoram; a busca as marca como instaladas, que é o correto).
- **`canonical_name` = versão da extensão (`3.5.3`)**: violaria `UNIQUE (tool_id, canonical_name)` com dois alvos e faria a troca de versão da extensão criar linhas novas para o mesmo arquivo.
- **Resolver as releases da extensão com um provider próprio**: duplicaria `http`/curadoria; a visão de release reaproveita os providers sem tocar neles.
- **`post_install` antes do move (como nas tools)**: o render de uma extensão é configuração da versão alvo, e o T9 precisa ver o arquivo no lugar; com o move antes e o desfazer em falha, `bin/` continua intacto em qualquer erro.
- **Apagar o overlay da série sempre**: quebraria a outra versão da mesma série que ainda tem a extensão.
- **Erro estruturado novo (`extension_incompatible`)**: as séries compatíveis vão na mensagem do `not_found` (o mesmo código que a CLI e a GUI já tratam); um `reason` novo exigiria tradução em todos os clientes sem ganho de ação (não há "instalar" automático para resolver).

## Consequências
- Instalar/remover Xdebug é dado de manifesto: outra extensão (`php_redis`, `php_imagick` com `archive: zip` e `install.target` pasta) segue o mesmo caminho.
- O M2-E2-T9 (`php.xdebug` instalando a extensão que falta dentro do próprio job) chama `install::install_extension(daemon, job, ext, None, Some("php@<série>"))`; ligar/desligar fica no overlay (toggle + quick settings), não aqui.
- O M2-E2-T5 (`tools.plan`) reaproveita `install::extension_targets` + `layout::extension::plan` para os itens `reason: extension` com `target`.
- `tools.list` não mostra extensões; a tela de Catálogo usa `tools.info`/`tools.search` (`kind`).
- Medido: `xdebug_install_online` (Xdebug 3.5.3 real de xdebug.org para PHP 8.4.27 NTS VS17): download + verificação + instalação em ~1,5 s, sha256 igual ao curado, overlay desligado, `php -n -d zend_extension="…" -m` lista `Xdebug`.
