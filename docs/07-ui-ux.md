# 07 — UI/UX e design system ("Apple-ish")

Meta: o Forgebox deve parecer um app de primeira linha do macOS rodando no Windows, sem parecer um site. Isso se obtém com **disciplina**, não com efeitos: hierarquia tipográfica rígida, grid de 4/8 px, poucas cores, materiais translúcidos usados com propósito, motion com física e estados sempre explicados.

Este documento é normativo para `apps/desktop/`. Exemplos de telas (wireframes) ficam em `docs/design/`.

## 1. Princípios
1. **Clareza antes de densidade.** Cada tela responde a uma pergunta: "o que está rodando?", "o que está errado?", "o que posso fazer agora?".
2. **Estado sempre visível e explicável.** Nenhum spinner sem texto. Nenhum erro sem causa + ação sugerida ("Porta 3306 em uso por mysqld.exe (XAMPP). Encerrar | Trocar porta").
3. **Direto, sem modais desnecessários.** Edição inline, popovers, sheets laterais. Modal só para destrutivo.
4. **Teclado em primeiro lugar.** Command palette (`Ctrl+K`), atalhos globais, navegação por Tab com foco visível.
5. **Motion com significado.** Animações informam origem/destino; springs (não ease-in-out lineares); respeitam `prefers-reduced-motion`.
6. **Nativo onde importa.** Moldura própria com cara de app do macOS (sidebar de vidro em altura total, controles da janela como bolinhas coloridas à direita na ordem do Windows; decisão do usuário de 2026-11-04 sobre o mockup [`docs/design/reference/glass-mockup.html`](design/reference/glass-mockup.html), M2-E1-T23), materiais do sistema (desfoque do DWM no Windows 10, Mica/Acrylic no 11), menu de contexto nativo, notificações do Windows, snap layouts funcionando (Aero Snap e `Win+setas` já; o menu do Windows 11 no hover do maximizar fica para o gate M2, [ADR-0035](adr/0035-window-chrome-materials.md) §6), DPI por monitor.
7. **Paridade GUI = CLI.** Toda ação mostra o comando `forge` equivalente no tooltip/rodapé ("Copiar comando"). O texto vem do `cli_template` da linha do método em `methods.ts` ([ADR-0037](adr/0037-cli-equivalent-templates.md)), nunca de string escrita à mão na tela. **Exceção (M2-E3-T9):** abrir no editor, no navegador e na pasta (`sites.open` com `editor`/`browser`/`explorer`, `shell.open_editor`) mostra o comando do programa subjacente (o editor configurado ou detectado com o caminho e a linha, o URL no navegador, `explorer <pasta>`), não um `forge`: a CLI não tem esses lançadores como verbo próprio (`forge site open --editor` existe, mas é só atalho para o mesmo método); o rodapé mostra o que o daemon vai executar. O terminal externo (`shell.open`) mantém `forge shell`.

## 2. Fundamentos visuais

### 2.1 Tipografia
- Família: `"SF Pro Text"` se disponível → `"Segoe UI Variable Text"` (Win11) → `"Segoe UI"` → `Inter` (embutida no bundle via `@fontsource`, latin + latin-ext; ver docs/08 §2.5). Monoespaçada: `"Cascadia Code"` → `"JetBrains Mono"` (embutida).
- Escala (px / line-height / weight): Display 28/34/600 · Title1 22/28/600 · Title2 17/22/600 · Headline 15/20/600 · Body 13/18/400 · Callout 12/16/400 · Caption 11/14/400 · Mono 12/18.
- `font-feature-settings: "tnum"` em números (portas, métricas) para alinhamento.
- Nunca texto abaixo de 11 px. Nunca justificado. Nunca caixa alta para ênfase (exceto labels de seção com tracking +4%).

### 2.2 Espaçamento e raio
- Grid 4 px; espaçamentos oficiais: 4, 8, 12, 16, 20, 24, 32, 40.
- Raios: controles 6 px; cards 10 px; sheets/popovers 12 px; janela 8 px (Win11 cuida).
- Bordas 1 px com cor `--stroke` (alpha), nunca cinza sólido.

### 2.3 Cor (tokens em `src/design/tokens.css`)
Fonte única: [`docs/design/tokens.json`](design/tokens.json) (DTCG). `pnpm -C apps/desktop tokens` gera `tokens.css` (temas, `data-vibrancy`, `data-contrast="high"`, `forced-colors`, `@theme` do Tailwind 4) e `tokens.ts`; `pnpm tokens:check` falha em CI se houver drift. Valores light dos estados são mais escuros que os abaixo (dark) para cumprir 3:1. `--stroke` é divisor decorativo (alpha 10%, isento de 3:1); bordas de controles usam `--stroke-strong` (≥ 3:1). Lint: sem literais de cor (ESLint `no-restricted-syntax`, stylelint `color-no-hex`) fora de `tokens.css`/`tokens.ts`, sem fonte < 11 px.

```
--bg-canvas        base da janela (transparente quando vibrancy ativa; sólido no fallback)
--bg-sidebar       sidebar sobre o material: transparente com Mica/Acrylic, --bg-sidebar-glass sobre o
                   desfoque do Windows 10 (claro rgba(246,244,250,.62), escuro rgba(38,36,46,.58)) / sólido
--fill(-hover|-pressed|-selected)  preenchimentos suaves (alpha 5-14 %): botão secundário, busca, chips,
                   linha selecionada da sidebar (raio --radius-item 7 px); --stroke-control: borda só no alto contraste
--window-minimize #FEBC2E  --window-maximize #28C840  --window-close #FF5F57  --window-inactive (cinza sem foco)
                   --window-dot-stroke (traço interno)  --window-glyph (glifo no hover)
--tool-1..8 + --fg-on-tool  ladrilhos de tool (cor escolhida pelo id, FNV-1a; 4,5:1 com o texto branco)
--bg-surface       cards, listas            --bg-surface-2  surfaces elevadas
--fg-primary       texto principal          --fg-secondary  texto secundário  --fg-tertiary labels
--fg-on-accent     texto/ícone sobre fundo --accent (4,5:1; branco no light, preto no dark e alto contraste)
--stroke           divisores (alpha 8–12%)
--accent           cor do sistema Windows (`SystemAppearance.accent` do forge-core; o `AccentColor` do CSS não é confiável no WebView2) com fallback #0A84FF
--state-running    #30D158   --state-starting #FFD60A   --state-stopped #8E8E93   --state-failed #FF6259 (dark; 4,5:1 sobre `--bg-surface-2`)   --state-updating #64D2FF
(o ui.color do manifesto não pinta a UI: sem garantia de contraste; os ladrilhos usam a paleta --tool-*)
```
- Light e dark completos. Dark é o padrão quando o sistema é dark. Contraste mínimo WCAG AA (4.5:1 texto, 3:1 UI).
- **Materiais** ([ADR-0035](adr/0035-window-chrome-materials.md) e o adendo M2-E1-T23): a janela inteira recebe o material e o CSS decide onde ele aparece — **só a sidebar** fica sobre o material (`--bg-canvas` transparente e `--bg-sidebar` = `--bg-sidebar-material` com `data-vibrancy="on"`), o painel de conteúdo (barra de ferramentas incluída) é **opaco** (`--bg-canvas-solid`) para legibilidade e performance. Política (`choose_effect`, função pura em `src-tauri/src/window.rs`), nesta ordem: o usuário desligou (`vibrancy: "off"` nas preferências da GUI), alto contraste, sessão RDP ou "Efeitos de transparência" desligado → **opaco**; Windows 11 build ≥ 22621 (22H2) → **Acrylic** (o backdrop do sistema, sem atraso ao arrastar); Windows 11 22000–22620 → **Mica**; Windows 10 1809+ → **desfoque do DWM** (`window_vibrancy::apply_blur`, sem tinta nativa: a sidebar pinta `--bg-sidebar-glass` por cima, `data-effect="blur"`), ou Acrylic com o opt-in `win10_acrylic` (o Acrylic do Windows 10 atrasa arrastar/redimensionar); mais antigo/desconhecido → opaco. A medição de arrasto/redimensionamento com desfoque × opaco no console físico do Windows 10 está no adendo da ADR. O efeito é aplicado pelo crate `window-vibrancy` e o `Result` dele decide o fallback (o `set_effects` do Tauri responde `Ok` no Windows 10 sem fazer nada e não é usado). Reavaliado quando o tema muda, quando a janela ganha foco (cobre transparência, alto contraste e reconexão RDP) e quando uma preferência muda. O shell põe em `<html>` `data-theme` (`light`/`dark`), `data-vibrancy` (`on` só com material em efeito; `off` pinta `--bg-*-solid` — sem material a área transparente ficaria preta), `data-effect` (`mica`/`acrylic`/`blur`/`none`), `data-contrast="high"` e `--system-accent` (`src/app/appearance.ts`, antes do primeiro paint por um script de inicialização e depois pelo evento `forge://appearance`; fora do Tauri, `?theme=&vibrancy=&effect=` fazem o mesmo). Diagnóstico: `FORGE_GUI_EFFECT=mica|acrylic|blur|none` força a tentativa (QA/medição). Os fatos do SO vêm de `forge_core::platform::SystemAppearance` (via `forge_ipc::base::platform`): `os_build`/`is_win11`, `remote_session` (RDP), `transparency` ("Efeitos de transparência"; o `prefers-reduced-transparency` do WebView2 reflete o mesmo interruptor), `high_contrast`, e `apps_light`/`taskbar_light` (tema dos apps e da barra de tarefas, que escolhe a variante dos ícones da bandeja, §7).

### 2.4 Iconografia
- Set único (Lucide, stroke 1.5) para UI; logos das tools em SVG monocromático + colorido (do registry).
- **Ícone de tool em toda tela que mostra uma** (Dashboard, Serviços, Catálogo, onboarding; `ToolTile` em `src/design/primitives`, M2-E1-T23): o SVG de `tools.icon` sempre como `<img>` com data URI (nunca SVG inline, §7/docs/11); SVG colorido aparece como é; SVG monocromático (`currentColor`/preto, ou sem pintura — dentro de `<img>` viraria um círculo preto) aparece branco sobre um quadrado arredondado na cor `--tool-N`; sem ícone, o mesmo quadrado com um monograma de duas letras (`mysql` → "My", `redis` → "Rd", `php-fpm` → "Pf"). A cor sai do id da tool (FNV-1a sobre 8 tokens), nunca do manifesto.
- Tamanhos: 16 (inline), 20 (lista), 24 (toolbar), 32/48 (cards).
- **Ícone do app (marca)** — fonte em [`docs/design/brand/`](design/brand/README.md), a partir da arte de referência do usuário (`reference-icon-tray.png`): caixa escura aberta com o prompt `>_`, camadas roxo/verde e laranja e tampa de vidro azul flutuante. Master vetorial `forgebox-icon.svg` (transparente, sem glow, sem halo em fundo claro) para 40/48/64/256 px e o conjunto do Tauri; 16/20/24/32 px são grades desenhadas pixel a pixel (menos camadas, prompt de 2 px, alinhadas à grade 2:1), não reduções. `apps/desktop/src-tauri/icons/icon.ico` (16, 20, 24, 32, 40, 48, 64, 256) é o recurso 32512 do `Forgebox.exe` (ícone do EXE, da janela e da barra de tarefas, e do futuro instalador) e é embutido com o mesmo id em `forge.exe`, `forgeboxd.exe`, `forgebox-helper.exe`, `forge-mcp.exe` e `forgebox-ctrl.exe` pelos `build.rs` (rc.exe do Windows SDK). Tudo é gerado por `pnpm -C apps/desktop icons`; `icons:check` falha se um arquivo divergir das fontes.

### 2.5 Elevação e profundidade
- Sombras só em popovers/sheets/toasts: `0 8px 24px rgba(0,0,0,.18)` dark / `.08` light. Cards não têm sombra, têm borda + surface.

## 3. Motion
- Biblioteca: Motion (framer-motion) com springs: `stiffness 380, damping 32` para layout; `260/26` para popovers; `500/40` para toggles.
- Durações máximas: micro 120 ms, transições 220 ms, sheets 280 ms.
- Transições compartilhadas (layoutId) entre lista → detalhe de serviço.
- Estados de serviço animam: ponto de status pulsa em `Starting`, "respira" em `Running` (sutil, 2 s), fica estático em `Stopped`, treme 1× em `Failed`.
- Progresso de download: barra com velocidade e ETA; ao concluir, morph para check.
- `prefers-reduced-motion`: tudo vira fade 100 ms.

## 4. Estrutura da janela

Decisão do usuário de 2026-11-04 (M2-E1-T23, aprovada sobre [`docs/design/reference/glass-mockup.html`](design/reference/glass-mockup.html); não re-discutir): a sidebar de vidro sobe até a borda de cima e não existe titlebar de largura total; o painel de conteúdo tem a própria barra de ferramentas com os controles da janela à direita.

```

│ Forgebox        (arrasto) │ Painel            ⌕ Buscar  Ctrl K   [▶ Iniciar tudo]   ● ● ●     │
│ [ Local             ▾ ]   ├──────────────────────────────────────── (min)(max)(fechar) ──────┤
│ ▦ Painel                  │ Conteúdo (opaco)                                                  │
```

- **Status no rodapé da sidebar** (`SidebarStatus`, M2-E1-T23; a barra de status inferior foi removida sem perder função): uma linha compacta com a conexão com o daemon e CPU · RAM, e embaixo os chips DNS e CA (preenchimento suave), que levam a `/diagnostics` (DNS: *ok* = habilitado e servidor rodando, *desligado*, *precisa de atenção*; CA: *ok* = confiável no usuário ou na máquina, *não confiável*, *sem CA*). Com a sidebar recolhida vira um ponto que leva a `/diagnostics` e fala tudo no nome (`aria-label` + `title`). **CPU/RAM = o próprio daemon** (`daemon.status.cpu_pct`/`rss_bytes`, API 1.1) **+ a stack** (CPU das instâncias; RAM de instâncias e pools PHP), do mesmo poll de 2 s das sparklines (`useStatusTotals`; só com a janela visível e focada, [ADR-0034](adr/0034-desktop-shell-architecture.md), adendo M2-E1-T9). Sem amostra (janela fora de foco desde o início, daemon desconectado) mostra o último valor ou nada, nunca zero inventado.
- **Shell e rotas** (M2-E1-T10, adendo da [ADR-0034](adr/0034-desktop-shell-architecture.md); `src/app`): `AppShell` = `Sidebar` em altura total ao lado do painel de conteúdo opaco (`--bg-canvas-solid`), que tem no topo a barra de ferramentas (`Titlebar`: título da seção, busca, **Iniciar tudo** como ação primária e os controles da janela) e embaixo o `ConnectionBanner` e a rota (M2-E1-T23; sem barra de status). Rotas do TanStack Router por código, uma por arquivo em `src/app/routes/` e cada tela um chunk lazy em `src/features/<id>/index.tsx`: `/dashboard`, `/services`, `/sites`, `/sites/$id`, `/php`, `/databases`, `/mail`, `/logs`, `/catalog`, `/catalog/$id`, `/terminal`, `/settings`, `/diagnostics` (fora da navegação: paleta, Configurações › Avançado, chips DNS/CA do rodapé da sidebar), `/onboarding` (portão: raiz sem `state/` leva para lá e mostra só a barra de ferramentas, com "Forgebox" como título) e `/__gallery` (só fora de produção); `/` redireciona para `/dashboard`. A tabela `src/app/features.ts` (rota, tarefa dona, grupo da sidebar, ícone) alimenta a sidebar e os placeholders; enquanto a tarefa dona não entrega, a tela é um `EmptyState` que nomeia a tarefa. **Toda rota continua navegável com o daemon parado**: o banner explica (*Conectando*, *Iniciando o daemon*, *Reconectando* ou *Daemon parado* com **Iniciar** e `forge daemon start`) e as ações dependentes do daemon ficam desabilitadas com o motivo em texto (`errors:capability.*`, ligado por `aria-describedby`).
- **Sidebar** (220 px; 56 px abaixo de 1100 px de largura da janela; altura total, sobre o material, borda direita `--stroke`): no topo a marca **Forgebox** numa faixa de 44 px que também arrasta a janela (`data-tauri-drag-region`), o seletor de contexto (dados em `shell/contexts.ts`: Local e o item desabilitado *Adicionar remoto (M6)*; cada contexto pode ter `accent`, aplicado como `--accent` na janela), depois os itens da tabela de rotas em grupos estilo Finder (`group` em `features.ts`: o primeiro sem título; *Dados* e *Ferramentas* com títulos cinza pequenos; sem bordas entre grupos), linhas de 28 px com ícone de linha na cor de destaque, seleção preenchida `--fill-selected` com raio de 7 px e contagens alinhadas à direita; no pé, Configurações, o status (acima) e a versão. Selos: serviços `● n ○ m` (rodando/parados, falho conta como parado), sites, Catálogo `↑N` (`tool.updates_available`) e Mail (não lidos de `mail.status`, **oculto** enquanto o método for `not_implemented` ou sem permissão). Os selos atualizam por evento no mesmo nó do DOM (seletores que devolvem números; nada remonta). Recolhida: só ícones com `aria-label` (nome + selo falado) e tooltip nativo `title` (Radix e motion ficam fora do primeiro paint). Rodapé: versão do daemon e estado do atualizador do app (*atualizações do app chegam na 1.0*; fluxo do M2-E1-T18, inativo na 0.2.0). **Iniciar tudo** (`services.start` sem alvos, pela fila de reconexão) saiu da sidebar e é a ação primária da barra do conteúdo (só ícone abaixo de 1100 px); continua na paleta e em `Ctrl+Shift+S`.
- **Slots** (`src/app/slots.ts`, para os épicos montarem telas sem editar o shell): `siteTabs` (abas do detalhe do site), `dashboardSections`, `attentionSources` (fontes do bloco Atenção: um *hook* `useItems()` por fonte, renderizado em um componente por fonte) e `settingsSections`. Um módulo `src/features/<id>/slots.ts` (carregado por glob, deve ser pequeno e registrar componentes `lazy`) ou qualquer módulo chama `registerSiteTab(...)` etc.; a ordem é `order` (100) e depois `id`. `DashboardSectionsHost` e `SiteTabsHost` (`src/app/hosts.tsx`) renderizam os registros, cada entrada com seu *error boundary*.
- **Janela** ([ADR-0035](adr/0035-window-chrome-materials.md), `src-tauri/src/window.rs`): sem decoração do Windows, transparente só quando um material é esperado na abertura (senão opaca com a cor `bg-canvas`, que evita o quadro preto antes de o WebView2 apresentar; um material que fique possível depois vale na próxima abertura), com a sombra do sistema e a borda de redimensionar invisível do Tauri (8 px fora da área visível nas laterais/base; no topo, os primeiros pixels da sidebar e da barra do conteúdo redimensionam). Criada **escondida**; o webview chama o comando `ready` depois de um duplo `requestAnimationFrame` que segue o primeiro commit do shell e só então ela aparece (sem flash branco; `--minimized` mantém escondida na bandeja; um vigia mostra a janela após 5 s se `ready` não vier).
- **Barra do conteúdo** (`src/app/shell/Titlebar.tsx`, 44 px, só sobre o painel de conteúdo, M2-E1-T23): título da seção à esquerda (texto, não heading; a página mantém o seu `h1`), espaço, slot da busca `Ctrl+K` (campo suave; a paleta da M2-E1-T14 abre por ele), a ação primária opcional da página e os `WindowControls` no canto direito. Tudo que não é controle é região de arrasto (`data-tauri-drag-region="deep"`), duplo clique maximiza/restaura. **Controles da janela** (`WindowControls.tsx`): três bolinhas de 12 px, 8 px entre elas, na **ordem do Windows à direita** — minimizar amarela (`--window-minimize`), maximizar/restaurar verde (`--window-maximize`), fechar vermelha (`--window-close`) — com traço interno fino (`--window-dot-stroke`); os glifos (traço, quadrado/restaurar, x) aparecem com o mouse sobre o grupo ou com foco de teclado; com a janela sem foco (eventos de foco do Tauri, `onFocusChanged`) as três ficam cinza (`--window-inactive`) e sem glifo, como no mockup. Cada botão é um alvo de 24×24 (os vizinhos se sobrepõem 4 px para manter os 8 px entre as bolinhas), alcançável por Tab na ordem minimizar → maximizar → fechar, anel de foco `--accent`, `aria-label` + tooltip nativo `title`, Enter/Espaço ativam; em `forced-colors` usam cores do sistema e mostram os glifos. Snap ao arrastar para a borda e `Win+setas` funcionam; o menu de *snap layouts* do Windows 11 no hover do maximizar fica para o gate (precisa de Win11 e, sem Win32 próprio, de suporte do WebView2/plugin; ver a ADR).
- **Tamanho mínimo** = **min(960×600, área de trabalho do monitor)** em pixels lógicos (`min_logical_size`, `window_state.rs`), aplicado na criação e **recalculado quando a janela muda de monitor ou de DPI** (`ScaleFactorChanged` e `Moved`; o SO só é chamado quando o valor muda, `needs_min_size_update`): arrastar para um monitor de outra área de trabalho com a mesma escala não gera evento de escala. Um notebook 1366×768 a 125 % com barra de tarefas de 50 px tem 1093×574 DIP de área (o mínimo vira 960×574) e 1440×810 a 150 % tem 960×540. **Degradação graciosa** (medida no `qa:check`, `qa/checks/matrix.spec.ts`, 960×540 e 1093×574 em claro/escuro, cenário `heavy`): abaixo de 1100 px de largura a sidebar vira só ícones; o documento nunca rola (sem barra de rolagem na janela): sidebar em altura total, barra do conteúdo fixa no topo do painel (sem barra de status) e cada tela rola **por dentro** do conteúdo; nenhuma tela passa de 100 % da largura. Elementos fora do fluxo (`sr-only`, popups) precisam de um ancestral `relative` dentro do contêiner que rola, senão estendem o documento (achado F-04 de `docs/design/qa/M2-E4-report.md`).
- Topo da sidebar é o **seletor de contexto** (Local · remotos). Contexto remoto muda a cor de destaque da janela e mostra latência/conexão ([13](13-remote-mode.md)).
- Janela lembra posição/tamanho/maximizada **por monitor** (`window-state.json` nos dados da GUI; volta encaixada na área de trabalho; com o monitor ausente usa o do outro monitor conhecido, senão centraliza 1200×800). Fecha → esconde na bandeja quando `close_to_tray` (padrão ligado) **e** a bandeja existe (M2-E1-T15); sem bandeja, fechar encerra a GUI (o daemon continua).
- **Instância única**: abrir o `Forgebox.exe` de novo traz a janela existente para a frente (restaura se minimizada); com `--minimized` a segunda execução não faz nada.
- **Dados da GUI** (preferências `prefs.json`, `window-state.json`, perfil do WebView2 em `webview/`): `%LOCALAPPDATA%\Forgebox\gui`, ou `<raiz>\state\gui` no modo portátil, ou `FORGE_GUI_DATA_DIR` (testes/QA). Nunca no `forgebox.toml` ([ADR-0034](adr/0034-desktop-shell-architecture.md) §5). Comandos `gui_prefs_get`/`gui_prefs_set` (chaves conhecidas: `theme`, `vibrancy`, `win10_acrylic`, `close_to_tray`; as demais ficam intactas para as features donas delas).

## 5. Telas

### 5.1 Onboarding (primeira execução, 4 passos, ≤ 12 interações)
1. Boas-vindas + escolher pasta raiz (`C:\Forgebox`) e diretório parked (`C:\Forgebox\www`), TLD (`.test`).
2. Escolher stack inicial (cards: Laravel · WordPress · PHP genérico · Node/Next · Vazio) → lista do que será baixado com tamanho total; versões ajustáveis.
3. Permissões e paridade: "Adicionar ao PATH" (toggle), "DNS automático para *.test (precisa de 1 confirmação de admin)" (toggle), "Confiar na CA local" (toggle, explica o diálogo do Windows), "Iniciar com o Windows", **"Modo paridade Linux (case-sensitive)"** ligado por padrão com explicação de uma frase ([15](15-linux-parity-case-sensitivity.md)).
4. Download com progresso por item e dicas; ao final: "Seu primeiro site: arraste uma pasta aqui ou crie um projeto".
- No M2 (M2-E2-T19, `apps/desktop/src/features/onboarding`): rota `/onboarding` (sem sidebar). O "< 2 min" deixou de ser critério, porque o tempo é dos downloads e da rede; o critério passou a ser **contagem de interações**: o caminho Laravel com os padrões termina em **5** (Continuar, escolher o card, Continuar, Instalar e configurar, Concluir) e o teste falha acima de 12, só com teclado também (Playwright). **Portão:** `OnboardingGate` leva a raiz não inicializada à rota; `OnboardingResume` (em `routes/root.tsx`) reabre o assistente quando o progresso guardado tem passo e não está concluído (a raiz já existe, então o portão não dispara). O estado vem dos comandos do T11 (`first_run_state`, `choose_root`, `onboarding_get|set`) atrás de `native.ts` (fake em memória no build `qa`, com `?portable=1`); cada escolha vai para `onboarding_set` na hora (o progresso é chaveado pela raiz atual, `key_for`; depois do `choose_root` o assistente regrava o estado inteiro do passo 1 na chave nova com `persistAll`), então fechar no passo 3 e abrir de novo retoma as escolhas e o passo. **Passo 1** (só daemon local com raiz escolhível): raiz (padrão `C:/Forgebox`), pasta parked (padrão `<raiz>/www`, segue a raiz até ser editada) e TLD (validado: rótulos DNS minúsculos e sufixo de uso local, a lista da allowlist do helper em [11](11-security.md) §1). "Continuar" faz, na ordem e uma vez cada (`choices.applied`): `choose_root`, `system.config_set tld` (só se o TLD mudou) e `sites.park`. Com daemon remoto ou raiz fixada por `FORGEBOX_ROOT`/portátil o passo some, e uma nota no topo diz por quê; sem o passo 1 o assistente inicializa a raiz (`start {initialize}`) ao abrir. **Passo 2:** cards = `tools.search` com `kind = stack` e tag `onboarding`, na ordem do índice, mais o "Vazio" embutido; `tools.plan {stack, specs}` mostra a lista com tamanhos e o total ("≈" com tamanho estimado); "Ajustar versões" chama `tools.releases` por ferramenta e uma série diferente replaneja (`specs: ["php@8.3"]`). **Passo 3:** PATH (oculto no modo portátil e no remoto), DNS automático (explica a única confirmação UAC), Confiar na CA (`tls.ca_install` escopo `current_user`, explica o diálogo do Windows), Iniciar com o Windows (API de autostart do E1; oculto no portátil/remoto) e paridade Linux (ligada; a frase é a de [15](15-linux-parity-case-sensitivity.md) §8; desligada vira `system.config_set case_sensitive false` seguido de `fs_parity.case_disable {dir: <pasta parked>}` no passo 4, porque o passo 1 já criou `www/` com a flag e o NTFS a herda por padrão para tudo que nascer dentro dela; a pasta ainda está vazia, então não há conflito. Sem o passo 1 (daemon remoto, portátil, raiz fixada, refazer a partir de Configurações) o cliente não conhece a pasta parked do daemon nem sabe se ela está vazia (ADR-0009), então só grava `case_sensitive false` e **não** chama `fs_parity.case_disable`). Nada roda antes de "Instalar e configurar". **Passo 4:** em ordem, paridade (se desligada), downloads, PATH, DNS, CA e inicialização, cada um com status, "Tentar de novo" e "Pular"; os downloads são um `tools.install` por item do plano (uma linha cada, com progresso, dicas e a causa quando falha) e "Tentar de novo" **replaneja** e instala só o que falta. Uma falha não interrompe os demais; um UAC recusado (`needs_elevation`) vira **pulado**, com o comando (`forge dns enable`) e "Tentar de novo". O resultado do DNS diz se o Windows roteia por NRPT ou se caiu no `hosts` (com o motivo) e que **curingas não resolvem no modo hosts**. Ao fim aparece "Seu primeiro site" (soltar uma pasta, ou digitar o caminho; `sites.add`) e o painel recolhível **Comandos equivalentes** lista cada comando que o assistente executa (renderizados pelas mesmas ações). **Refazer:** a linha `onboarding` de Configurações → Geral (M2-E3-T16, `settings/sections/general.tsx`) abre `/onboarding` de novo; o assistente não registra seção própria de Configurações. As escolhas de TLD e paridade usam a ação `setConfig` (`system.config_set`) de `actions/system.ts`.

Só com a janela oculta, minimizada ou sem foco o poll chega a 0 chamadas. Mudar isso (por exemplo cadência menor da barra) é decisão do usuário ou de um gate.

### 5.10 Terminal
- Terminal integrado (xterm.js + ConPTY via Rust) com PATH do Forgebox; abas por site ("Terminal em loja.test", PHP/Node certos); comando `forge` autocomplete.
- **Implementação (M2-E3-T15, `apps/desktop/src/features/terminal`, abas em `src/state/terminals.ts`):** `@xterm/xterm` 6 com os addons fit, web-links, search e unicode11; renderizador WebGL com queda automática para o DOM (sem WebGL, contexto perdido, RDP). Fonte `--font-mono` (Cascadia → JetBrains Mono embutida, funciona offline) e cores dos tokens (`--bg-surface`, `--fg-primary`, `--accent`, `--state-*`).

## 7. Bandeja (tray)
- Ícone (arte do usuário, [docs/design/brand](design/brand/README.md)) = ícone do app + um selo no canto inferior direito (metade do ícone, anel de recorte de 1 px), sempre diferente também pela forma, nunca só pela cor. Estado agregado: **running** (ponto verde: tudo que está habilitado rodando), **starting** (anel azul girando: 8 quadros, ~8 fps só enquanto inicia, quadro estático com movimento reduzido), **stopped** (quadrado vermelho: nada rodando), **updating** (seta azul: atualização pendente ou job de instalação/atualização), **warning** (triângulo âmbar com `!`: algum serviço falhou ou está em crash-loop enquanto outros rodam), **error** (`!` vermelho em disco: daemon inacessível ou todos os serviços habilitados falharam); `base` (sem selo) antes do primeiro estado. Precedência: error > warning > starting > updating > running > stopped (M2-E1-T15).
- Precedência do estado agregado (M2-E1-T15, `tray/model.rs`): vence o primeiro cuja condição vale, nesta ordem — **error** (daemon inacessível: conexão perdida, reconectando ou parado depois de já ter conectado; ou todos os serviços habilitados em `failed`/`crashed`) > **warning** (algum serviço em `failed`/`crashed`) > **starting** (algum em `starting`) > **updating** (`tool.updates_available.count > 0`, job `tools.install|update|rollback|remove|add_local` em andamento, instância em `maintenance` ou atualização do app anunciada pelo updater) > **running** (algo rodando) > **stopped** (nada rodando, inclusive sem serviços). "Habilitados" = instâncias com `autostart`; sem nenhuma, todas. Antes da primeira resposta (abrindo, primeira conexão, onboarding) o ícone é `base`.
- Menu nativo (estrutura da arte de referência, `tray/model.rs` → `tray/menu.rs`): cabeçalho "Forgebox · <contexto>" com o ícone do app e submenu de contexto ("● Local", "Adicionar remoto (M6)" desabilitado) · linha de status desabilitada com ponto colorido ("Todos os serviços em execução" / "n de m serviços em execução" / "n com falha" / "Daemon indisponível") · Abrir painel · Gerenciar serviços › (um item de marcação por instância: marcado = rodando, clique inicia/para; ocupado em `starting`/`stopping`/`maintenance`; mais "Abrir Serviços") · Sites › (abre `SiteDto.url` no navegador pelo cliente, via plugin opener: funciona com remoto) · PHP CLI › (rádio: itens de marcação, o atual marcado, clique = `tools.use {tool: php}`; acompanha `tool.current_changed`) · separador · Iniciar todos (só quando algum habilitado está parado/falho) · Reiniciar todos (habilitado se algo roda) · Parar todos (habilitado se algo roda ou inicia) · separador · Ver logs (`/logs`) · Mail (n não lidos; `/mail`) e Terminal, ocultos enquanto `mail.status`/`terminal.open` estão em `hello.not_implemented` · separador · Configurações (`/settings`) · Sair. Diferença consciente da referência: a linha de status é um item próprio (menus nativos não têm subtítulo) e o muda não tem rádio nativo (itens de marcação fazem o papel). Rótulos do namespace i18n compartilhado `tray` (pt-BR + en-US), refeitos quando a UI troca de idioma (`set_language`).
- Ações do menu usam o contexto ativo e um `request_id` novo por clique (ADR-0009); as de serviços são jobs (`services.start|stop|restart`, alvos vazios = todos). A navegação mostra a janela e emite `forge://navigate` com a rota (o webview só aceita `/services`, `/logs`, `/mail`, `/settings`); Terminal (item e clique do meio) reaproveita o evento do atalho global, então quem roda `terminal.open` é o webview.
- **Sair**: diálogo nativo "Parar serviços e sair" / "Manter serviços e sair" / "Cancelar". Parar envia `daemon.stop {keep_services: false}` e sai após a resposta ou 5 s, o que vier primeiro; manter sai sem chamar o daemon.
- Ícones do menu: glifos monocromáticos no estilo Lucide (grade 24, traço 2), rasterizados em 16 px (a célula de ícone do muda no Windows) na cor do texto do menu. Tema do menu: o Windows desenha os menus pop-up e o Tauri (tao) só permite seguir o modo de app do sistema ("AllowDark"); nem Tauri nem muda fixam o menu da bandeja no tema claro/escuro escolhido no app. Fallback: o menu segue o modo de app do Windows (`SystemAppearance.apps_light`; alto contraste = claro) e os glifos são desenhados para esse tema. Um flyout no estilo Fluent (webview próprio, como na arte de referência) fica como melhoria futura possível, fora do escopo do M2.
- Contexto ([13](13-remote-mode.md)): primeira linha do menu mostra o contexto ativo ("● Local" ou "● hml (Linux)") com submenu para trocar; todas as ações do tray agem sobre o contexto ativo; com remoto selecionado o ícone ganha um pequeno indicador (ponto roxo no canto superior esquerdo, a sobreposição `tray/remote-<light|dark>.ico` composta sobre o ícone do estado) e o tooltip diz o nome do remoto, para nunca parar um serviço na máquina errada.
- Hover mostra tooltip com resumo (serviços rodando/falhos, PHP CLI ativo, contexto).
- Clique esquerdo abre/foca a janela; clique direito abre o menu; clique do meio abre o terminal global.
- Notificações nativas do Windows (toast) para: serviço caiu e foi reiniciado, update instalado, download concluído, alerta de desempenho, túnel pronto (com URL copiável). Agrupadas e com "não mostrar de novo" por tipo.
- Toasts (M2-E1-T16, `src-tauri/src/notifications.rs`, `tauri-plugin-notification` 2.4.0, a última linha abaixo do MSRV; chamado só pelo Rust, a webview não recebe permissão `notification:*`): o ator da bandeja alimenta um `NoticeEngine` com cada evento, então os toasts saem com a janela oculta. Tipos: `service_restarted` (`service.crashed` seguido de `service.running` da mesma instância; queda sem volta não notifica), `update_installed` (`tool.updated`), `install_completed` (`tool.install.completed`). O daemon roda a instalação de verdade num job interno `tool.install <tool>@<versão>` (dentro de `tools.install <specs>`, de `tool.update <tool> <de> -> <para>` ou de `tool.rollback <tool> <série>`, também nos updates agendados, que não passam por `tools.update`) e o `tool.install.completed` carrega o id desse job interno; por isso a instalação de um update/rollback é calada por ferramenta (o motor guarda os jobs `tool.update`/`tool.rollback` em andamento a partir de `job.started` e os esquece em `job.done|failed|cancelled`) e o toast é o de update. Não há regra sobre `job.done` de `tools.install`: os jobs internos já emitem o evento. Ordem das regras: evento reproduzido no resume (`seq` <= `hello.last_event_seq` da conexão) nunca notifica; tipo silenciado nunca notifica; rajada do mesmo tipo é agrupada na borda final: o primeiro evento abre uma janela de 5 s e, ao fim dela, UM toast representa todos os itens distintos ("3 serviços foram reiniciados: nginx, mysql, redis"; `toast.<tipo>.body_many` com `{count}` e `{list}`, até 5 nomes e "…"), então um evento isolado aparece 5 s depois. A réplica do resume e o estado da conexão chegam à bandeja por caminhos diferentes e sem ordem fixa (o cliente reassina com `resume_from` antes de publicar o estado novo), então ao sair de Connected o motor passa a segurar os eventos (no máximo 512) e só os julga quando o `hello` da nova conexão fixa o cursor. "Não mostrar de novo" é o array `muted_notifications` (ids dos tipos) em `prefs.json`, gravado pela tela de Configurações com `gui_prefs_set`; textos no namespace `notifications` (`toast.<tipo>.title|body|body_many`, `types.<tipo>`, `dont_show_again`). O gancho de alerta de desempenho (`NoticeEngine::performance_alert`) existe e fica desligado (adiado, ADR-0044); toast de túnel pronto é M3. **Clique no toast NÃO está implementado**: `Tray::notification_clicked(tipo)` (foca a janela e emite `forge://navigate` para `NoticeKind::route`: `/services`, `/catalog`) existe e é testada, mas o plugin 2.4 não tem callback de ativação nem argumento de lançamento no desktop, então nada a chama a partir de um toast real. Ligar isso exige um notificador com callback de ativação no processo (por exemplo `tauri-winrt-notification` `on_activated`) atrás de uma trait do forge-core reexportada por `forge_ipc::base` (ADR-0035: sem Win32 no `src-tauri`); fica adiado para uma tarefa própria a ser agendada, não é item de verificação humana do M2-E4-T11. Fora do build instalado (`target/debug|release`) o Windows mostra o toast com o AUMID do PowerShell (medido em release, ver docs/STATUS.md); a verificação do toast no build instalado (AUMID próprio) continua sendo item humano do M2-E4-T11.
- O tray pertence ao processo da GUI (`Forgebox.exe`). Se a GUI não estiver aberta, o daemon continua rodando sem tray; `forgeboxd` nunca cria UI. Opção "Iniciar com o Windows" sobe a GUI minimizada na bandeja.
- Implementação: `tray-icon` do Tauri 2 em `apps/desktop/src-tauri/src/tray/` (`mod.rs` ator, `model.rs` modelo puro, `menu.rs` lado nativo, `icons.rs` bitmaps), ícones por estado em `apps/desktop/src-tauri/icons/tray/<estado>-<light|dark>.ico` embutidos no `Forgebox.exe` (`include_bytes!`; estados `base`, `running`, `starting-0`…`starting-7`, `stopped`, `updating`, `warning`, `error`, mais a sobreposição `remote`), cada um com 16/20/24/32 px (100/125/150/200 %, escolhido pelo DPI da bandeja) e com variante para barra clara (`-light`) e escura (`-dark`, aro mais claro na caixa) escolhida por `SystemAppearance.taskbar_light`; gerados de `docs/design/brand` por `pnpm -C apps/desktop icons`; o tamanho vem do fator de escala do monitor principal (onde fica a barra) e a sobreposição remota é composta pixel a pixel ("source over"). O anel de `starting` anda a ~8 fps (125 ms) só enquanto o estado é `starting`; com `prefers-reduced-motion` (informado pelo webview via `tray_motion`) fica no quadro 0.
- Modelo e eventos (ADR-0011): um ator `TrayModel` por contexto ativo, com o seu próprio `events.subscribe` pelo `Contexts` da ponte (dono `tray`, não fecha quando a página recarrega). Só conecta depois do primeiro paint (`ready`, ou o watchdog de 5 s). O snapshot (`services.status`, `sites.list`, `php.list`, `mail.status` quando implementado, mais o `hello`) é buscado uma vez por conexão e de novo só após `lagged`/`reset`, frame perdido, fim do stream ou evento que o peça (instância desconhecida → `services.status`; `site.*` → `sites.list`; PHP instalado/removido/atualizado → `php.list`) — nunca por polling; falhas tentam de novo com espera dobrando (3 s até 60 s). Renderizações têm debounce de 100 ms (a primeira mudança depois de um período quieto sai na hora, rajadas viram uma) e esperam o menu fechar (botão direito pressionado até um item escolhido, clique/entrada no ícone ou 5 s); o menu anterior fica vivo para nunca destruir o que está na tela. Medido no teste contra servidor forge-ipc real: pior latência evento→menu ~100 ms. O estado duplica parte das stores do webview de propósito: a bandeja funciona com a janela oculta.
- Capturas de QA (`scripts/qa/capture-tray.ps1`, PrintWindow, funciona em RDP): barra de tarefas, área de notificação, flyout de overflow e o menu real aberto (`-MenuOfProcess <pid> -OpenMenu`; `-Submenu <n>` abre o submenu na posição `n` do menu raiz — 0 contexto, 3 Gerenciar serviços, 4 Sites, 5 PHP CLI — e compõe os níveis abertos numa imagem). O `tray-icon` 0.25 ignora cliques quando `Shell_NotifyIconGetRect` falha (no Windows 10, ícone escondido no overflow); nesse caso o script abre o flyout de overflow e clica de novo. O tema do menu segue o modo de app do Windows, então menu claro e escuro e barra clara e escura só se capturam trocando o tema do sistema: isso fica para a verificação humana do gate do M2 (M2-E4-T11), no console real com o ícone fixado na área visível, anexando as capturas ao PR ao lado de [reference-icon-tray.png](design/brand/reference-icon-tray.png). Testes automatizados nunca mudam o tema do usuário.

## 9. Acessibilidade e i18n
- Navegação completa por teclado; `aria-*` via Radix; foco visível com anel `--accent`; textos alternativos em ícones de status (não só cor).
- pt-BR e en-US no lançamento; strings em `src/i18n/`; formatos de data/número via `Intl`.
- i18next + react-i18next; um namespace por feature em `src/i18n/{pt-BR,en-US}/<ns>.json` (`common`, `shell`, `errors`, `tray`, `notifications`, `palette`, + um por feature), carregados sob demanda, chaves tipadas (`src/i18n/i18next.d.ts`: **todo namespace novo entra em `Resources`**). Interpolação `{var}` (mesma sintaxe no Rust).
- Idioma: preferência do usuário > idioma do SO (`navigator.language`, que no WebView2 segue o idioma do Windows) > pt-BR. A troca em runtime re-renderiza sem reload e chama o comando Tauri `set_language`, que mantém `src-tauri/src/i18n.rs` (bandeja e notificações, `include_str!` dos namespaces `tray` e `notifications`) em sincronia.
- Formatadores (`src/i18n/format.ts`): bytes (`410 MB`), duração (`2h 14m`), relativo (`há 2 min`), percentual, número e data via `Intl`; números na UI usam a classe `tabular-nums` (`TNUM_CLASS`).
- Mensagens da API nunca são traduzidas: a UI localiza a partir de `code` e `details` (namespace `errors`).
- Lint: `eslint-plugin-i18next/no-literal-string` em JSX (`eslint.i18n.js`; allowlist de marcas e comandos `forge`). Teste de paridade (`src/i18n/i18n.test.ts`) cobre toda chave/placeholder de todos os namespaces automaticamente.
- Pseudo-locale `pseudo` (acentos, +40 % de comprimento, placeholders preservados) só para QA: aceito apenas fora do modo `production`.
- Escala de fonte do sistema respeitada; testar em 100/125/150/200%.

Medição, harness e QA visual: [ADR-0036](adr/0036-frontend-test-strategy-cold-start.md) (`pnpm perf:startup`, `scripts/e2e-desktop.ps1`; `scripts/gui-e2e.ps1` para as telas do E2 contra o daemon real, [§12](#suíte-live-do-e2-m2-e2-t20)).
- Orçamentos medidos (M2-E4-T4, `pnpm -C apps/desktop qa:perf`): Playwright (Edge, build `--mode qa`, cenários do fakeBridge; `playwright.perf.config.ts`, `qa/perf/*.spec.ts`) roda o conjunto 3 vezes (`scripts/qa-perf.mjs`, `FORGE_PERF_RUNS`) e grava `qa/out/perf/run-<n>/<spec>.json` + `summary.json` (média e coeficiente de variação). Cada spec falha acima do limite: interação sem long task nem clique > 50 ms (passada fria dos chunks só relatada); lista de 500 sites com mediana ≥ 55 fps (rAF sem o limite de 30 Hz da sessão RDP, `--disable-frame-rate-limit`) e sem long task > 50 ms; enxurrada de 500 eventos/s por 2 s com ≤ 1 commit por frame da linha tocada e 0 renders das demais (contador de render só-QA em `src/qa/render-counter.ts`, chamado sob `import.meta.env.MODE === "qa"` e ausente do bundle de produção, verificado por sentinela em `src/qa/sentinel.test.ts`; a sondagem de métricas é desligada tirando o foco da janela); daemon lento (`slow`, 1,5 s por chamada): mediana de navegação < 100 ms; daemon parado: banner "reconectando" em < 1 s, navegação < 100 ms e, após o resume, 0 ids de evento duplicados e 0 perdidos no livro de eventos (entrada do feed de Atividade). Interação: a passada fria também abre/fecha a folha de detalhe do serviço e digita na busca; a passada quente usa cliques reais do Playwright (eventos confiáveis, registrados pelo Event Timing) na barra lateral. ### Portão de paridade GUI/CLI (M2-E4-T5)

Toda ação do registro `defineAction` tem amostras de entrada em `apps/desktop/qa/parity/gui-commands.test.ts`, que carrega todo módulo `src/actions/*.ts` por `import.meta.glob` (uma tela nova com `src/actions/<nome>.ts` entra no gate sem editar o teste, e uma ação sem amostra o faz falhar); o teste grava o comando `forge` renderizado em `qa/parity/gui-commands.json` (versionado; o teste falha se o arquivo divergir, e `FORGE_PARITY_UPDATE=1 pnpm -C apps/desktop exec vitest run qa/parity` o regenera). `crates/forge-cli/tests/gui_parity.rs` faz `Cli::try_parse_from` em cada comando e exige que ele caia na linha `METHODS` da ação. Cobertura: todo método com `cli` não vazio, mutante ou não, é alcançado por alguma ação ou está em `qa/parity/cli-only.yaml`: `cli_only` (de propósito sem GUI, `reason` obrigatória), `query` (consulta ou stream que a GUI só exibe; a `reason` obrigatória nomeia a tela que mostra o dado) ou `pending` (ação que uma tela de M2 ainda vai adicionar, com a tarefa; vale também para métodos não mutantes disparados pelo usuário, como `daemon.doctor`, `tls.ca_export`, `logs.read`). Um método listado que uma ação já alcança faz o teste falhar (a lista só encolhe). O gate do M2 (M2-E4-T11) roda com `FORGE_PARITY_STRICT=1`, e então `pending` precisa estar vazio. O teste "Copiar comando" garante que o texto escrito na área de transferência é exatamente a string renderizada, com caminhos do Windows com espaço entre aspas.

### Suíte live do E2 (M2-E2-T20)

`powershell -NoProfile -File scripts/gui-e2e.ps1 [-SkipBuild] [-Release] [-Grep <texto>]` roda o `Forgebox.exe` de debug (feature `custom-protocol`, `dist/` embutido) contra um `forgeboxd` real numa raiz portátil temporária, dirigido por Playwright sobre o CDP do WebView2 (`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<livre>` só no ambiente do teste). Código em `apps/desktop/e2e/live/` (`fixture.mjs`, `support.ts`, `parity.ts`, `e2.live.spec.ts`), `playwright.live.config.ts` e `pnpm -C apps/desktop e2e:live`. A raiz da fixture traz PHP 8.3.36 e 8.4.27 (`php.exe` e `php-cgi.exe` falsos de `crates/forge-daemon/tests/fixtures/fake_php.rs`, FastCGI de verdade), nginx, MySQL e Mailpit falsos (os mesmos `fake_*.rs` do daemon, compilados com `rustc`), um registry de fixture (cópia do oficial sem assinatura, com a stack `fixture-php` e a ferramenta `fixture-slow`, cuja URL https aponta para um socket local que nunca completa o TLS; `cargo run -p forge-daemon --example live_seed` grava a linha do registry como `trusted_unsigned` no store) e portas livres para tudo. Nada toca HKCU Run, os repositórios de certificados nem a NRPT: o cenário de onboarding desliga PATH, DNS, CA e inicialização automática, e o site é criado sem HTTPS.

Cenários, em série e numa só sessão do app: (1) onboarding com a stack de fixture, (2) iniciar e parar serviços no tile e na tela Serviços, com a marca de performance `forge:start-click` até `forge:start-shown` (o loading "Starting" do tile em < 50 ms; medido 1,1 a 1,8 ms), (3) criar site, (4) trocar o PHP do site entre as duas versões (o `fastcgi_pass` do vhost e o pool da série seguem), (5) um quick setting do MySQL (`max_connections`, vai ao `my.ini`), (6) alternar a extensão `xsl` do PHP 8.4 (overlay `10-forgebox.ini`), (7) instalar do catálogo e cancelar (o job termina `cancelled` e nada fica em `bin/`), (8) matar o `forgeboxd` (status diferente de `connected` em < 2 s, medido 138 a 185 ms) e conferir que as telas ressincronizam com o mesmo documento (sem reload) e que os eventos voltam a fluir. O nono teste é a varredura de paridade: todo `[data-action]` visto nas rotas do E2 tem `data-forge-cli`, está no golden `qa/parity/gui-commands.json` e a linha passa pelo clap do `forge` real (`--help` sai com 0); os 3 testes de `e2e/live/parity.test.ts` provam que o validador falha numa página ruim. O teardown mata a árvore de processos (GUI, WebView2, daemon, serviços falsos) e apaga a pasta temporária; o script falha se algo sobrar. O idioma muda para en-US pelo seletor de Configurações (o `--lang` do WebView2 não muda `navigator.language`) e as telas são trocadas por `history.pushState`, sem reload. O primeiro uso é o portão do E2; o checklist do §11 das seis telas está em [docs/design/qa/m2-e2-checklist.md](design/qa/m2-e2-checklist.md).
