# 05 — Providers de download e auto-update

## 1. Providers nativos (`forge-provider::provider::*`)

Um provider resolve `(tool, constraint, variants) → Vec<Release{version, url, sha256, size, variants, published_at}>`. Manifestos escolhem o provider por `type`. Providers nativos existem porque alguns upstreams têm APIs/índices próprios que valem a pena parsear com cuidado.

| type | Upstream | Como resolve | Checksum | Observações |
|---|---|---|---|---|
| `php-windows` | windows.php.net | `GET https://downloads.php.net/~windows/releases/releases.json` → chaves `"8.4"`, `"8.3"`… cada uma com `version` e variantes `ts-vs17-x64`, `nts-vs17-x64`, `ts-vs16-x64`… contendo `zip.path`, `zip.size`, `zip.sha256`, `debug_pack`, `devel_pack`. Versões anteriores em `releases/archives/` (listagem HTML parseada; sha256 via `.sha256` quando existir) | sha256 oficial | Builds de QA (`qa/`) só no canal preview. Observado em 26/10/2026: 7.4 (vc15), 8.0–8.3 (vs16), 8.4–8.5 (vs17) |
| `apache-lounge` | apachelounge.com | Parse das páginas `download/VS17/` e `download/VS18/`, arquivos `httpd-2.4.NN-YYMMDD-win64-VS1x.zip`; `.txt` com sha; mod_fcgid e outros módulos na mesma página | sha256/sha512 publicados | Site sem API; cache agressivo; fallback para `releases:` estático no manifesto |
| `nginx-org` | nginx.org | Parse de `nginx.org/en/download.html` (mainline/stable) → `nginx-1.NN.N.zip` | sem checksum upstream (só PGP) → verificamos PGP com chave embutida | |
| `github-release` | api.github.com | `releases` + filtro por regex de asset; rate-limit tratado com ETag/cache; token opcional | `*.sha256`/`checksums.txt` quando existir | Usado por caddy, frankenphp, mailpit, minio, meilisearch, cloudflared, bun, mongosh… |
| `mysql` | dev.mysql.com | Parse de `downloads/mysql/` (zip "Windows (x86, 64-bit), ZIP Archive") e `archives/`; md5 publicado → **exigimos sha256** via `downloads.mysql.com/archives/get/p/23/file/...` + hash calculado e fixado no registry (`releases:` curado) | sha256 curado | API instável → lista curada no registry, atualizada por bot |
| `mariadb` | mariadb.org / archive.mariadb.org | `https://downloads.mariadb.org/rest-api/mariadb/<series>/` (REST oficial) → `mariadb-X.Y.Z-winx64.zip` (o `.msi`, o `-debugsymbols.zip` e a pasta `winx64-packages/` são ignorados) com sha256/sha512 | sha256 oficial | API REST estável |
| `postgresql-edb` | enterprisedb.com | Lista curada (`postgresql-<ver>-windows-x64-binaries.zip`); sha256 curado | sha256 curado | EDB não publica índice; bot do registry atualiza |
| `nodejs-dist` | nodejs.org/dist | `index.json` oficial (versões, lts, files) + `SHASUMS256.txt` por versão → `node-vX-win-x64.zip` | sha256 oficial | Canais `lts`, `current` |
| `python-embed` | python.org | `python-3.X.Y-embed-amd64.zip` + também "nuget" `python.3.X.Y.nupkg` (contém pip) | sha256 (via `/ftp/python/3.X.Y/` listagem md5 → curado) | |
| `http` | genérico | URL com placeholders `{version}`, `{series}`, chaves de variante (`{compiler}`) e `vars` ([04](04-tool-manifest-spec.md) §1.5); versões via `releases:` estático ou `version_source: {url, regex|json_path}` | obrigatório | Para tudo que não tem API |
| `local` | arquivo local/zip | `forge tool add-local <zip>` com manifesto embutido | sha256 calculado e exibido | |
| `wsl` / `docker` *(v2)* | WSL2 / Docker Desktop | Para tools sem build Windows (Valkey, DragonflyDB, KeyDB, RabbitMQ) | imagem digest | Ver [12-stacks-compat.md](12-stacks-compat.md) |

Todos os providers:
- Cacheiam metadados em `state/registry/cache/<provider>/` com TTL e `ETag`.
- Respeitam `prefs.proxy` (sistema ou manual) e `prefs.offline` (só cache).
- Expõem `published_at` para a UI mostrar "lançado há 3 dias".
- Devolvem **todas** as variantes para que a UI mostre NTS/TS, VS16/VS17 com explicação ("NTS é o recomendado para FastCGI").

### 1.1 Implementação (`forge_provider::provider`, M1-E2-T3)
- **API:** `trait Provider { fn resolve(&self, ResolveRequest { tool, constraint, variants, channel }) -> Result<Vec<Release>> }` e `ProviderRegistry::for_spec(&ProviderSpec)` (único `match` por tipo de provider; `ProviderSpec` é o `Provider` do manifesto). `ProviderRegistry::resolve` percorre `source.providers[]` em ordem e devolve o primeiro que tiver releases. `python-embed` ainda devolve `not_implemented` (fica para depois); `local` não resolve nada remoto.
- **`Release`:** `version`, `url`, `sha256`/`sha512` (opcionais), `size` (só exato), `variants`, `published_at`, `signature: Option<SigRef>` (PGP; o *sujeito* é o arquivo ou o documento de checksums, como no Node), `file_name`, `checksum_url` e `tags` (`stable`/`mainline`/`legacy`, `lts`, `lts:<Codinome>`, `qa`, `archive`, `curated`). Resultado já filtrado por `constraint`, canal e `variants` pedidas, sem duplicatas e **ordenado preferido-primeiro** (versão mais nova; depois a ordem e o `default` de `versioning.variants`): o seletor padrão é o primeiro item. Sem canal, pré-releases ficam de fora; canal desconhecido é `invalid_input`. Valores de variante fora de `versioning.variants[].values` (ex. `vc11`) são descartados.
- **sha256 curado:** quando o upstream não publica hash (nginx, `archives/` do PHP), o `sha256`/`size` de `source.releases[]` com a mesma versão e variantes é mesclado na release. Sem hash nenhum a release sai com `sha256: None` e quem baixa deve recusar (ou exigir `--allow-unverified`).
- **Hash em segundo documento** (Node `SHASUMS256.txt`, Apache Lounge `.txt`, `checksums.txt`/`*.sha256` do GitHub, `checksum.url` do `http`): lido na hora só para as `ProviderConfig::max_checksum_fetches` (20) releases mais novas; as demais trazem `checksum_url` e `resolve_checksum()` busca sob demanda.
- **Cache/rede:** `state/registry/cache/<provider>/<sha256(url)[..24]>.{body,json}` com `ETag`/`Last-Modified`; dentro do TTL (1 h) não há requisição, depois revalida (`If-None-Match`, 304 renova); falha de rede, 5xx ou rate limit do GitHub servem o cache vencido (404 não); `prefs.offline` serve só cache (sem cache: `conflict`). Proxy como no download; token do GitHub (`prefs`) vai só para o host da API. Todo pedido tem `tokio::time::timeout`; I/O de cache via `tokio::fs`.
- **`php-windows`:** `releases.json` (variantes `ts|nts` × `vcNN|vsNN` × `x64`; x86 é ignorado; `size` é texto arredondado e não é reportado) + `releases/archives/` (listagem HTML, sem hash: só existe `sha1sum.txt`, observado em 26/10/2026) + `qa/` somente se `qa: true` **e** o canal pedido tiver `prerelease`. Rebuilds `8.3.36-1` viram a versão `8.3.36+1` (build metadata; como semver `-1` seria pré-release menor que `8.3.36`); `8.1.27RC1` vira `8.1.27-RC1`. A listagem de archives/qa é "melhor esforço".
- **`apache-lounge`:** uma página por `builds[]` (`download/VS17/`, `VS18/`); só `win64`; `compiler` e `arch=x64` como variantes (VS17 e VS18 vêm lado a lado); `.txt` (SHA1–SHA512) e `.asc` ligados na release; `asset` customizado (módulos) é regex sensível a maiúsculas com grupo `version`. Fallback para `releases:` se o site estiver fora.
- **`nginx-org`:** seções Mainline/Stable/Legacy de `download.html`, zip + `.zip.asc`; página sem nenhum zip é `invalid_input` ("layout mudou").
- **`mariadb`:** índice de séries + `<série>/` de todas as séries do índice (cache por TTL, 4 por vez); a constraint é aplicada às releases reais em `filter::finish`; série com falha é ignorada (erro só se todas falharem); séries não `Stable` (RC, Preview) viram pré-release (`13.1.1-rc`); a URL é montada em `<base>/<versão>/<arquivo>`.
- **`nodejs-dist`:** `index.json` (somente versões com `win-x64-zip`), canal chamado `lts` filtra pela tag `lts`; `SHASUMS256.txt` + assinatura `.sig`.
- **`github-release`:** primeira página (100) de `/repos/<repo>/releases`; hash do campo `digest` do asset (`sha256:`) ou do asset de checksum do manifesto; drafts nunca, pré-releases só com `prerelease: true`.
- **`http`:** placeholders `{version} {series} {major} {minor} {patch}`, chaves de variante e `vars` (o valor mapeado pela variante cuja chave está no mapa); `{url}`/`{file}` só em `checksum.url`; `version_source.json_path` aceita o subconjunto `$ .chave ['chave'] [n] [*]`. Placeholder desconhecido é `config_invalid`.
- **`mysql` / `postgresql-edb`:** só `source.releases[]`, validadas (URL http(s) e `sha256` obrigatórios; todos os problemas juntos em `config_invalid`); nenhuma requisição.
- Testes: `crates/forge-provider/tests/providers.rs` (fixtures gravadas em 26/10/2026 em `tests/fixtures/<provider>/`, servidor axum local) e `providers_online.rs` (`#[ignore]`, um `*_online` por provider: `cargo test -p forge-provider --test providers_online -- --ignored`). As fixtures do Node (30 primeiras entradas + 2 LTS de `index.json`), PHP `archives/`/`qa/` e GitHub (6 releases) são recortes dos documentos reais.

## 2. Download
Implementação: `forge-provider::download` (`DownloadManager`, ator da fila; cada download é um job de `forge_core::jobs`).
- API: `download(DownloadRequest { urls, expected_size, expected_sha256, dest, priority }) -> JobId`. Resultado em `job.done`: `{path, size, sha256, source, mirror_failures[]}` (`sha256` é o calculado). Erros de pedido (sem URL, esquema não http/https, sha256 que não tem 64 hex) e `prefs.offline` falham na hora, sem criar job (offline = `conflict`).
- Fila com prioridade (`UserAction` > `AutoUpdate`, FIFO dentro da prioridade), paralelismo 2 downloads × 4 conexões. Cancelar um job ainda na fila não ocupa vaga. O mesmo arquivo pedido de novo para o mesmo destino devolve o job existente; se ele ainda espera vaga e o novo pedido tem prioridade maior (ex.: `UserAction` sobre um `AutoUpdate` já enfileirado), a prioridade da entrada na fila sobe; outro destino é `conflict` (um `.part` por arquivo).
- Retomada por `Range`; arquivo parcial em `tmp/downloads/<chave>.part`, onde `<chave>` são os 16 primeiros hex do sha256 esperado (ou do sha256 da primeira URL, sem sha). Ao retomar, o `.part` é re-hasheado (`spawn_blocking`); se a verificação final falhar após uma retomada, o parcial é descartado e o download recomeça uma vez antes de culpar o mirror. Servidor que ignora `Range` (200) reinicia do zero.
- Arquivos ≥ 50 MB cujo servidor anuncia `Accept-Ranges: bytes` usam até 4 conexões `Range` escrevendo cada uma sua fatia do `.part` pré-alocado; as posições ficam em `<chave>.part.json` para retomar só o que falta. O sha256 desses é calculado no fim (streaming só no modo de uma conexão). Buffers de 1 MiB; escrita e hash sempre em `spawn_blocking`.
- Progresso: `job.progress` a cada 250 ms com `bytes_done`, `bytes_total`, `pct`, `speed_bps` (EMA, alfa 0,3) e `eta_secs` (campos `speed_bps`/`eta_secs` foram acrescentados a `JobProgress`); a mensagem traz a fonte ("Baixando de downloads.php.net").
- Falhas transitórias (conexão cortada, timeout, 408/429/502/503/504) retomam no mesmo mirror até 3 vezes (espera 1 s × tentativa); outros erros HTTP passam ao mirror seguinte. Cada falha de mirror é registrada com o motivo (`mirror_failures`) e entra na mensagem de erro final (`io`, ou `verification_failed` se todos serviram bytes inválidos).
- Limite de banda opcional (token bucket compartilhado, rajada de 1 s, alterável em execução); pausa em conexão medida: o motor de updates (§4.1) consulta uma função injetada (`MeteredProbe`) antes de checar/baixar em segundo plano; a implementação sobre o `NetworkCostManager` do Windows fica com o daemon (M1-E5-T2).
- Proxy: sistema por padrão (reqwest com a feature `system-proxy`: Internet Settings/WinHTTP do Windows e depois variáveis `HTTP(S)_PROXY`), `Direct` ou manual (`DownloadConfig.proxy`, vindo de `prefs.proxy`).
- Cancelamento (`job.cancel`): mantém o `.part` e não emite `job.done`.

## 3. Verificação
Implementação: `forge_provider::verify` (`Verifier::verify(path, Expect) -> VerifyReport`, tudo em `spawn_blocking`, buffers de 1 MiB; [ADR-0017](adr/0017-verify-extract-stack.md)). Divergências são `verification_failed` (a CLI sai com 6); expectativas malformadas (hex com tamanho errado, chave pública inválida) são `invalid_input`.
1. Tamanho (quando conhecido).
2. SHA-256 (ou SHA-512). Obrigatório. Sem hash → só com `--allow-unverified` (`Expect::unverified()`): o sha256 é calculado mesmo assim e o relatório sai com `unverified: true` para o aviso persistente no card.
3. Assinatura quando disponível: PGP destacado (`.asc` armored ou `.sig` binário: nginx `.zip.asc`, Node `SHASUMS256.txt.sig`, Composer `.sig`; PostgreSQL via EDB não tem), verificado com keyring **embutido** (`nginx`, `nodejs`: chaves atuais listadas pelo upstream em 26/10/2026, em `crates/forge-provider/keys/`) ou armored vindo do registry; minisign (registry e o próprio Forgebox; só assinaturas *prehashed*, verificadas no mesmo passe do hash). Releases antigas de Node assinadas por releasers que saíram da lista ativa falham no PGP: o provider trata PGP de versões antigas como opcional (o sha256 continua obrigatório) ou o registry fornece as chaves antigas.
4. Authenticode do `.exe`/`.dll` principal (quando assinado pelo upstream: Memurai, HeidiSQL, cloudflared) via `forge_core::platform::CodeSign` (`WinVerifyTrust`, assinatura embutida e catálogos do sistema, sem checagem de revogação) → exibimos o publisher; o chamador pode fixar o nome exato (`Signature::Authenticode { expected_publisher }`; o campo correspondente no manifesto ainda não existe no schema e entra com o instalador, M1-E2-T4). Não assinado, não confiável ou de outro publisher → `verification_failed`.

## 4. Políticas de atualização (por tool, sobrescrevível pelo usuário)

| Política | Comportamento |
|---|---|
| `manual` | Nunca checa. Usuário clica "Verificar". |
| `notify` | Checa; mostra badge e notificação; nada é baixado. |
| `auto-patch` *(padrão para runtimes e web servers)* | Baixa e instala patch dentro da mesma série (8.3.36 → 8.3.37); troca pools blue/green (`forge_fcgi::Switcher::switch(de, para)`, [03 §2.2](03-engine.md)); mantém `retention` versões. |
| `auto-minor` | Também segue minor (1.28 → 1.30 do Nginx). Nunca cruza major. |
| `auto` | Tudo, inclusive major. Só para tools sem estado (cloudflared, composer). |

Regras:
- **Bancos de dados nunca são auto-atualizados** (dados em `data/` exigem upgrade de schema; `mysql_upgrade`/`pg_upgrade`). Política fixa `notify` com assistente de upgrade manual que faz backup antes.
- O usuário escolhe janela (`quiet_hours`) e se quer updates em conexão medida.
- Toda atualização gera entrada no **histórico** com botão **Rollback** (re-aponta pools/`current` para a versão retida; nunca apaga a anterior antes da nova passar no health).
- Para PHP: ao atualizar dentro da série, migra `ext/` extra (Xdebug etc.) e re-renderiza `conf.d/`. Se uma extensão não for compatível com o novo build (ex. mudança vs16 → vs17 numa série, o que não acontece dentro de uma série), a atualização é bloqueada com explicação.

### 4.1 Implementação (`forge_provider::update`, M1-E2-T5, [ADR-0027](adr/0027-update-engine-active-version-rollback-retention.md))
- **Ator `update-engine`** (`UpdateEngine::spawn(supervisor, UpdateDeps, UpdateConfig)`): `check(tool|todas) -> Vec<AvailableUpdate>`, `apply(ApplyRequest) -> JobId`, `rollback(RollbackRequest{tool, série}) -> JobId`, `history`, `status` e os ganchos do agendador `next_check_at(tool, agora)` / `run_scheduled(tool, agora)`. No máximo uma operação por `(tool, série)`: o mesmo alvo devolve o job em curso, outro é `conflict`. Checagens rodam fora da mailbox; updates e rollbacks são jobs.
- **Injetado**: `ToolCatalog` (manifesto + `allow_run`; `forge_registry::Registry` implementa), `ReleaseSource` (`ProviderRegistry` implementa; hash em segundo documento resolvido antes do download), `ArchiveFetcher` (`DownloadFetcher`: `tmp/downloads/<arquivo>`, sha256/tamanho do release, prioridade `AutoUpdate` no agendador e `UserAction` para o usuário, cancelado junto com o job), `PoolSwitcher { switch(PoolSwitch{tool, series, from, to, from_version, to_version}), serving(tool, versão) }` (o daemon delega a `forge_fcgi::Switcher`; `NoPools` quando não há pool) e `MeteredProbe` (função). O re-render usa o `TemplateRenderer` já injetado no `Layout`.
- **Política efetiva**: `tools.update_policy` (override do usuário, `ToolVersionRepo::set_update_policy`) ou `update.policy`; `category: database` nunca passa de `notify` (`manual` continua `manual`). Override por versão/instância ainda não existe.
- **Linha de update**: série (`series_key`) + variantes escolhidas pelo usuário (`ts`); variantes `derive: from_provider` (compilador) ficam fora. **Versão ativa** da linha = alvo do registro `completed` mais recente do histórico (update ou rollback); sem histórico, a mais nova instalada que nenhum update `failed` teve como alvo (`policy::active_versions`, usada também pelo daemon para escolher a versão do pool de uma série).
- **Check**: para cada linha, a release estável mais nova acima da ativa dentro do alcance da política (`notify`/`manual`/`auto-patch` = mesma série, `auto-minor` = mesmo major, `auto` = qualquer), preferindo o mesmo build (mesma variante derivada). `AvailableUpdate {series, from, to, kind: patch|minor|major, policy, automatic, pinned, installed, blocked, release}`. Build novo com outro compilador e `update.migrate` presente sai `blocked` com explicação (aplicar é `conflict`). Depois de um rollback a linha fica **fixada** (`pinned`): o update aparece, mas não é automático até o usuário aplicá-lo.
- **Apply** (job `tool.update <tool> <de> -> <para>`): `update_history` `started` → download + instalação lado a lado (`Layout::install_from_archive`, `current` intocado; versão já instalada é reaproveitada) → `update.migrate` (`copy_dir` relativo às duas pastas; `only_missing` mantém os arquivos do build novo; links não são seguidos) → re-render das ações `render` de `install.post_install` para a versão nova (`Layout::rerender`: `conf.d` da série aponta para a versão exata) → `PoolSwitcher::switch` (tools `service.kind: pool`) → `current` segue se apontava para uma versão da mesma linha → `completed` → retenção → `tool.updated` (`ToolUpdateEventPayload` = `ToolVersionChangePayload` + `series`, `job_id`, `update_id`, `rollback_of`, `removed`). Falha → `failed` com a mensagem; troca que falha re-renderiza para a versão antiga e remove a versão que o próprio job instalou.
- **Retenção** (só depois da troca): versões instaladas da linha mais antigas que a nova (série da antiga ou da nova) além das `update.retention` mais novas são removidas por `Layout::remove_version` (recusa `current` e versões com instâncias; renomeia para `.<pasta>.forgebox-removed-<id>` e apaga), menos as que um pool ainda serve (`serving`). Problemas viram `warnings` no relatório.
- **Rollback** (job `tool.rollback <tool> <série>`): desfaz o update `completed` mais recente da série: re-render para a retida, `switch(ativa → retida)`, `current` volta, `update_history` ganha a linha `rollback` (`rollback_of`) e o update vira `rolled_back` na mesma operação; `tool.rollback`. Sem update para desfazer ou sem versão retida → `not_found`.
- **Histórico**: migração `0003` (`update_history.series`, `rollback_of`), `forge_core::store::UpdateHistoryRepo`, id `UpdateId`.
- **Agendador**: `next_check_at` = última checagem + `check_interval` ± 10 % (determinístico por tool; primeira checagem 60 s depois), fora de `quiet_hours` (hora local; vai para o fim da janela) e, com `[updates] metered = "pause"`, 30 min depois em conexão medida; `manual` = nunca (`at: None`). `run_scheduled` revalida janela e medição na hora (`deferred: quiet_hours|metered`), checa e aplica os automáticos. O loop é do daemon (M1-E5-T2).
- Testes: `crates/forge-provider/tests/update.rs` (cenário de aceite 8.3.36 → 8.3.37 → rollback com provider, fetcher e `PoolSwitcher` falsos; retenção com três versões; versão servida por pool não é removida; `notify`; banco nunca automático; `quiet_hours` e conexão medida; troca que falha; uma operação por série) e `tests/update_fetch.rs` (`DownloadFetcher` contra o servidor axum local).

## 5. Atualização do próprio Forgebox
- `tauri-plugin-updater` com `latest.json` em `https://github.com/forgebox/forgebox/releases/latest/download/latest.json`, assinado com chave minisign do projeto; modo `passive` no Windows.
- O daemon tem seu próprio canal: a GUI atualizada pede ao daemon para se auto-substituir (`forgeboxd --self-update <path>`): valida assinatura, para pools e serviços de forma graciosa **ou** usa handoff (novo daemon herda Job Objects via `DuplicateHandle` — v1.1), troca binário, reinicia.
- Canais: `stable`, `beta`. Changelog renderizado na UI antes de aplicar.

## 6. Bot do registry
GitHub Action (`registry/.github/workflows/bump.yml`) roda a cada 6 h: executa cada provider, detecta novas versões, calcula sha256 para upstreams sem hash, abre PR com a lista `releases:` atualizada e mudanças de `latest`. Humano aprova (ou auto-merge para patch). Assim o catálogo nunca depende de "alguém lembrar".

## 7. Offline e ambientes corporativos
- `forge bundle export php@8.3 nginx mysql@8.4 -o stack.fbx` gera um pacote (zip + manifestos + hashes) para instalar em máquinas sem internet (`forge bundle import`).
- Proxy corporativo: usa configuração do sistema (WinHTTP) por padrão; permite CA corporativa extra (`prefs.extra_ca_bundle`) para os downloads.
- Registry espelhado interno: `forge registry add file://\\servidor\forgebox\index.yaml` (fonte `Dir`; o espelho tem de manter o `index.yaml` assinado, senão só carrega como `trusted_unsigned`). O cache em `state/registry/<nome>/` permite abrir o catálogo sem rede: se a fonte falha, `load` serve o último catálogo verificado com um aviso; `refresh` (job explícito) reporta a falha.
